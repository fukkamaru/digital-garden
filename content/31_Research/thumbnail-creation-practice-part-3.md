ここまでの会話では、**YouTubeサムネイル用HTMLを「Webページ」ではなく「AI向けデザイン設計書」として読み取り、添付された実素材を使って完成画像を生成できるか**を、実際のファイル一式で確認しました。

## 今回の目的と前提

今回ユーザーから渡されたものは、以下の3点です。

- YouTubeサムネイルの設計内容を記述したHTMLファイル
- 主素材画像 `main_construction_yellow.png`
- 副素材画像 `texture_material_yellow.png`

HTMLについては、ブラウザ表示をそのまま画像化するのではなく、**DOM・CSS・`data-*`属性・座標・タイポグラフィ・色・画像スロット・禁止事項などをAIが設計情報として解釈する**という前提でした。

HTML自身にもこの方針が明示されており、「3840×2160のYouTubeサムネイルを生成するための設計仕様であり、完成レンダーではない」「ブラウザプレビューを最終画像として再現しない」と指定されています。

つまり今回確認したかったのは、

> HTML → ブラウザで再現 → スクリーンショット

ではなく、

> HTML設計書 + 実素材 → AIが設計意図を解釈 → 完成サムネイル画像を生成

というワークフローです。

## HTML設計書に記述されていたデザイン

キャンバスは**3840×2160、16:9**で定義されています。背景はオフホワイト `#F7F7F5`、本文色はチャコールブラック `#111315`、強調色は濃いブルー `#005B96`、補助線・枠線はグレー `#A4A9AD` です。フォントはNoto Sans JPを第一候補とする日本語サンセリフ系です。

デザイン方向はHTML内で **`clean industrial editorial`** と定義されています。主メッセージ・副メッセージ・視覚フックも明示されていました。

内容を整理すると、

- 主訴求：「縞鋼板の防滑性向上なら『塗る』すべり止め材」
- 副訴求：「ローラーで簡単施工」
- 視覚フック：鮮やかな黄色の防滑材、高粘度・粗粒感のあるテクスチャ
- 基本構図：左＝文字、右＝施工写真
- 左側は独立した白いパネルではなく、オフホワイトから写真へ自然にフェードする構成
- 黄色はあくまで施工材そのものの色として使い、文字や装飾には使わない
- 強調色のブルーは「塗る」だけに限定
- 余白を積極的に残し、バッジ・アイコン・追加コピーなどで埋めない

という設計です。

## 主素材画像の使い方

`main_construction_yellow.png` は**優先順位1のメインビジュアル**として指定されています。

配置は設計座標で、

- X = 1240
- Y = 0
- 幅 = 2600
- 高さ = 2160

となっており、画面右側を大きく占有します。

トリミング・構図上の重要ポイントとして、

- ローラー
- ローラーを持つ作業者の手
- 縞鋼板の凹凸
- 鮮やかな黄色の防滑材
- 未施工の銀色縞鋼板との境界

を残すことが指定されています。

特に、**黄色に塗られた部分だけではなく未施工の銀色部分も見せる**ことで、「縞鋼板へ塗布している」という状況を一目で伝える設計です。

工場内の奥行きや背景は残してよいものの、主役より目立ってはいけないという指定もあります。

## 左側の可読性処理

施工写真の上から、画面左側にオフホワイトのグラデーションを重ねる設計です。

グラデーションは左端ではほぼ完全な `#F7F7F5` で、右へ向かうにつれて透明になります。設計上はおよそ73%地点で完全に透明になります。

この処理の目的は、

- 白い四角形を置いた「パネル」に見せない
- 文字の可読性を確保する
- 右側の施工写真と左側のテキストエリアを自然につなぐ

ことです。

HTML内でも「separate boxed panel にしない」と明示されています。

## メインコピー

メインコピーは2行構成です。

1行目：  
**縞鋼板の防滑性向上なら**

2行目：  
**「塗る」すべり止め材**

設計座標は、

- X = 190
- Y = 180
- 幅 = 2020

です。

1行目は、

- 166px
- Weight 700
- `#111315`

2行目は、

- 202px
- Weight 900
- 基本色 `#111315`

で、**「塗る」だけを `#005B96` に変更**しています。

ここで重要なのは、「塗る」という単語の意味そのものを視覚的な差別化ポイントにしていることです。

つまり訴求の中心は、

**縞鋼板向け**  
→ **すべり止め**  
→ **テープではなく「塗る」材料**

という構造です。

文字にはアウトラインや装飾的な影を付けず、左側のオフホワイト背景とのコントラストだけで読ませる設計です。

## 副コピー

副コピーは、

**ローラーで簡単施工**

です。

設計上は、

- X = 200
- Y = 900
- 126px
- Weight 700
- `#111315`

となっています。

文字の左側には、

- 幅92px
- 高さ10px
- グレー `#A4A9AD`

の短い水平線を置く設計です。

この線は装飾というより、主コピーから副コピーへの階層を整理する編集的な処理です。

## 黄色い材料テクスチャの副素材

`texture_material_yellow.png` は、画面左下に配置する**副ビジュアル**です。

座標は、

- X = 190
- Y = 1330
- 幅 = 980
- 高さ = 560

です。

この素材で見せる対象は、

- ヘラ
- ヘラから垂れる黄色い材料
- 高粘度
- 骨材による粗いテクスチャ
- 混合容器の開口部分

です。

役割は、施工後の黄色い床だけでは伝えにくい、

**「これは粘度と粒状感を持つ、塗るタイプの防滑材である」**

という製品特性を補足することです。

ただし、別の商品広告のように独立して強調するのではなく、あくまで**補助的な視覚情報**として扱う指定です。

枠線はグレー `#A4A9AD` のみで、強調色の青は使用しません。キャプションも付けません。

## 色の役割分担

今回の設計では色の使い分けがかなり明確です。

- 黄色：防滑材そのもの
- オフホワイト：左側の情報領域
- チャコールブラック：基本テキスト
- 濃青：キーワード「塗る」
- グレー：副コピー前の線、テクスチャ画像の枠

黄色を文字や装飾に使わない理由は、**黄色い防滑材そのものを画面内でもっとも強い色として維持するため**です。

したがって、「黄色だから見出しも黄色にする」といった一般的な色合わせは意図的に禁止されています。

## 明示的な禁止事項

HTMLでは、AIが勝手にデザインを盛らないように禁止事項も指定されていました。

禁止対象には、

- 黄色の見出し文字
- 黄色のUI枠
- 黄色の装飾パネル
- 青い背景パネル
- 青い枠
- バースト型バッジ
- 吹き出し
- 太い文字アウトライン
- 大きな赤文字ブロック
- 製品缶
- ハンマー
- 防滑テープ
- コンクリート補修表現
- ロゴ
- ウォーターマーク
- UI表現

などが含まれています。

これは今回のテーマを、

**縞鋼板 × 塗るすべり止め材 × ローラー施工**

から逸脱させないためのガードレールです。

## 今回実際に行った画像生成

HTMLの内容を読み取った後、その設計内容を画像生成側の指示へ変換しました。

生成時には、

- HTML自体は描画しない
- 施工写真を右側の主役にする
- 左側をオフホワイトのグラデーション領域にする
- メインコピー2行を正確に使用する
- 「塗る」のみ青色
- 「ローラーで簡単施工」を副コピーとして配置
- 黄色い材料のテクスチャ写真を左下に配置
- 黄色を写真以外の装飾には使わない
- 不要なバッジ・パネル・コピー・ロゴを追加しない

という条件を明示して完成サムネイルを生成しました。

結果として、生成画像は設計書の主要な構成をかなり直接的に反映したものになりました。

完成画像では、

- 左：白〜オフホワイトの情報領域
- 右：ローラー施工写真
- 上左：2段のメインコピー
- 「塗る」のみ青色
- 中左：「ローラーで簡単施工」
- 左下：黄色い材料が垂れるテクスチャ写真

という構成が形成されています。

## 今回確認できたこと

今回のテストから確認できた重要な点は、**HTML設計書方式は画像生成AIへの受け渡しフォーマットとして実用可能**だということです。

特に有効だった情報は、

- `data-source-file` による素材ファイルの対応付け
- `data-role`
- `data-priority`
- `data-layout`
- `data-crop-focus`
- `data-composition`
- `data-preserve`
- `data-color-policy`
- `data-typography-policy`
- `data-spacing-policy`
- `data-text-policy`
- `data-image-policy`
- `data-do-not-show`

です。

単にCSSだけを書くのではなく、

**「何を」「なぜ」「どの優先順位で」「どう見せるのか」**

を意味情報としてHTMLに併記しているため、画像生成AI側が設計意図を理解しやすくなっています。

今回のHTMLは、一般的なWebページとしてのHTMLというより、

**DOM + CSS + 座標情報 + デザインルール + AI向けメタデータ**

をまとめた、機械可読な**デザインブリーフ兼レイアウト仕様書**として機能しています。

## 現時点のワークフロー

今回実施した流れをまとめると、

```text
実素材を用意
    ↓
YouTubeサムネイルのデザインを決定
    ↓
HTML設計書に記述
    ├─ DOM
    ├─ CSS
    ├─ 座標
    ├─ コピー
    ├─ 色
    ├─ タイポグラフィ
    ├─ 素材ファイル名
    ├─ crop-focus
    ├─ composition
    ├─ priority
    └─ 禁止事項
    ↓
HTML + 素材画像をAIへ渡す
    ↓
AIがHTMLを「設計図」として解釈
    ↓
実素材を使って完成画像を生成
    ↓
16:9 YouTubeサムネイル完成
```

という形です。

重要なのは、**HTMLのブラウザレンダリング結果を中間成果物として必要としない**ことです。

今回の方法ではHTMLそのものが、

**人間にも読める／AIにも読めるデザイン設計フォーマット**

になっています。

## 今回の到達点

今回のチャットで実際に確認したのは、

**「AI向けHTML設計書 + 個別の実素材画像」という形式をそのまま画像生成AIへ渡し、HTMLをWebページとしてレンダリングせずに、完成サムネイルまで生成できる**

という点です。

したがって、今後この方式を標準化する場合は、HTMLを単なるレイアウトコードではなく、

**サムネイル制作ブリーフを機械可読化したデザイン設計書**

として扱うのが適しています。

今回の構成では特に、

**主訴求1つ**  
→ 「塗る」すべり止め材

**視覚フック1つ**  
→ 黄色く塗布される縞鋼板

**補助情報**  
→ ローラー施工

**製品特性の補足**  
→ ヘラから垂れる高粘度・粗粒テクスチャ

という情報階層が明確に整理されています。

### 引き継ぎ用要約

- 実施内容：HTML設計書と2枚の素材画像を使い、HTMLをレンダリングせずにYouTubeサムネイルを生成した。
- 主要判断：HTMLはWebページではなく「AI向け機械可読デザイン設計書」として扱う。
- 成功した要素：`data-source-file`、座標、crop-focus、composition、priority、各種policy、禁止事項まで書く方式。
- 完成構成：左にコピー、右にローラー施工、左下に材料テクスチャ。「塗る」のみ青。
- 作成物：完成サムネイル画像。
- 次の具体的な検討事項：このHTML設計書のフォーマットを今後のサムネイル案件でも再利用できるよう、**共通テンプレート化するかどうか**。
