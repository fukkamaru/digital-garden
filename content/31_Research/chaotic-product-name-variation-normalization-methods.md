# 表記ゆれの多い品名データを段階的に正規化する方法

語順、全角・半角、記号、空白、属性の欠損が一つの品名列に混在する場合、単一の巨大な置換式で完成形を作ろうとしない。**元値を残し、段階ごとに処理と判定を分ける方式**が、最も説明・修正・検証しやすい。

本ノートの例は、[[kyoto-patty-029-sample-business|Kyoto Patty 029の架空事業設定とデータ設計]]に合わせた架空データであり、実データの品名や値は掲載しない。

## まず決めること

「同じ品名」と判定するための要素を先に決める。たとえば、品名・規格・味が一致して初めて同一とするのか、味が欠けていても同一候補として扱うのかで、必要なルールは変わる。

| 項目 | 例 | 扱い |
| --- | --- | --- |
| 表記だけの違い | 全角／半角空白、`ｽﾓｰｸ`／`スモーク`、`120Ｇ`／`120g` | 自動正規化の候補 |
| 語順の違い | `スモーク 120g`／`120g スモーク` | 要素を分けてから再構成する候補 |
| 必須要素の欠損 | `京パティ ミニ 120g` | 自動確定せず例外にする |
| 未登録の値 | `140g` | マスタ追加の確認対象にする |
| 意味の衝突 | `120g 140g` | 誤入力として例外にする |

## 現実的な標準フロー

```text
Rawの品名を保持
  → 文字種・空白だけを整形
  → 表記別名マスタで完全一致照合
  → 未一致の行だけを要素別に解析
  → 必須要素とマスタを検証
  → Standardの統一品名を作る
  → 判定不能・矛盾行は例外一覧へ
```

最初から全行を複雑な正規表現へ通すのではなく、確実に判定できる表記を先に対応マスタで吸収し、残った少数の行だけを解析・確認する。これが、候補数が有限な業務データでは最も保守しやすい。

## 架空データによる受入例

| Rawの品名 | 空白・文字種の整形後 | 統一品名 | 判定 | 例外理由 |
| --- | --- | --- | --- | --- |
| `京パティ ミニ　ｽﾓｰｸ 120Ｇ` | `京パティ ミニ スモーク 120g` | `京パティ ミニ 120g スモーク` | 変換可 | — |
| `京パティ ミニ120g　スモーク` | `京パティ ミニ120g スモーク` | `京パティ ミニ 120g スモーク` | 変換可 | 別名マスタで確認済み |
| `京パティ ミニ 120g スモーク` | `京パティ ミニ 120g スモーク` | `京パティ ミニ 120g スモーク` | 変換不要 | — |
| `京パティ ミニ 120g` | `京パティ ミニ 120g` | — | 要確認 | 味がない |
| `京パティ ミニ スモーク 140g` | `京パティ ミニ スモーク 140g` | — | 要確認 | 規格が未登録 |
| `京パティ ミニ 120g 140g スモーク` | `京パティ ミニ 120g 140g スモーク` | — | 要確認 | 規格が複数 |

この表は、変換処理の受入テストとして維持する。ルールを変えた場合も、既存の期待値が変わっていないことを確認する。

## 選択肢と使い分け

| 方法 | 向く状況 | 長所 | 注意点 |
| --- | --- | --- | --- |
| 完全一致の別名マスタ | 取扱品・別名の候補が有限 | 説明しやすく、Power Queryで扱いやすい | 未登録値は変換されない。ただし、それを例外として検知できる。 |
| 段階的な置換マスタ | 空白・記号・略称など、意味を変えない小さな差だけを整える | 既存データに段階的に追加できる | 順序による連鎖置換をテストする。 |
| 要素別の解析 | 品名、規格、味などの要素が比較的安定している | 語順が変わっても統一品名を再構成できる | 要素ごとのマスタと必須条件が必要。 |
| 正規表現 | 入力構造が安定し、組み合わせが多い | 多数の同型パターンを一度に検査できる | 正規表現対応環境が必要。全体一致と例外テストが必須。 |
| 人手確認の例外キュー | 欠損・矛盾・新規値がある | 誤変換を防ぎ、マスタ改善へつなげられる | 例外を放置しない担当・確認頻度を決める。 |

## 推奨するハイブリッド方式

実務では、次の組み合わせを基本とする。

1. 空白・文字種など、意味を変えない整形だけを行う。
2. 整形後の品名を別名マスタと完全一致で照合する。
3. 一致しない行だけについて、規格・味などを抽出して個別マスタと照合する。
4. 必須要素が一つでも欠ける、または複数候補が出る場合は統一品名を作らない。
5. 例外一覧を確認してから、必要に応じて別名マスタや受入テストへ追加する。

この方法では、日常的な表記ゆれの大半をマスタで吸収しつつ、想定外の値を静かに誤変換することを防げる。

## Power Queryでの実装イメージ

最初に、元の`品名`列を残したまま、整形済み列を追加する。空白の扱いは[[パワークエリで文字列前後のスペースを削除して、連続するスペースを1つにする|Power Queryで文字列の前後・連続スペースを整理する]]の関数を用いる。

次に、整形済み品名を別名マスタと完全一致で結合する。

```m
Table.NestedJoin(
    品名整形済み,
    {"品名_整形済み"},
    MstProductAlias,
    {"別名_整形済み"},
    "AliasMaster",
    JoinKind.LeftOuter
)
```

`MstProductAlias`には、少なくとも次の列を持たせる。

| 列 | 役割 |
| --- | --- |
| `別名_整形済み` | 変換前の候補値。照合キー。 |
| `商品コード` | 統一後に参照する識別子。 |
| `統一品名` | Standardで表示する品名。 |
| `ルール種別` | 文字種整形、語順違い、旧表記など。 |
| `優先順位` | 段階的置換を使う場合の適用順。 |
| `確認状態` | 確認済み、保留、廃止など。 |

部分文字列を順に置換する必要があるときは、[[Power Query：List.Accumulateを使った置換マスタによる一括置換]]の推奨例のように、置換前・置換後・優先順位を明示する。文字列の一部を扱う意図がある場合は、`Replacer.ReplaceText`を使う。これは、元のテキストに含まれる指定文字列を置き換える関数として定義されている。[Microsoft Learn](https://learn.microsoft.com/en-us/powerquery-m/replacer-replacetext)

## 正規表現を使う場合の境界

正規表現は、品名の構造が一定で、候補の組み合わせだけが多い場合に限って有効である。たとえば「品名 + 規格 + 味」の3要素が必ずあり、各要素の候補を検証できる場合は、全体一致で抽出できる。

一方、Power Queryの`Text.Replace`やVBAの`Replace`へ正規表現文字列を渡しても、正規表現としては評価されない。Power Queryで正規表現を使わずに済む候補集合なら、対応マスタを優先する。正規表現を採用する場合は、正規表現対応の環境を明示し、抽出できなかった値を例外へ送る。初期案の失敗理由は[[regex-based-product-name-normalization-initial-review|正規表現による品名表記ゆれ置換の初期案と制約]]を参照する。

## 運用で残す列

| 列 | 目的 |
| --- | --- |
| `品名_Raw` | 受領時の元値。変更しない。 |
| `品名_整形済み` | 空白・文字種だけをそろえた中間値。 |
| `商品コード` | マスタ照合の結果。 |
| `統一品名` | 分析・レポートで使用する値。 |
| `判定` | 変換可、変換不要、要確認。 |
| `例外理由` | 欠損、未登録、複数候補、形式不明など。 |
| `ルールバージョン` | どの変換規則で判定したか。 |

`Raw`、`Standard`、例外一覧を分ければ、後から規則を見直しても変換前後の差分を追跡できる。個別の変換設計は[[product-name-notation-normalization-design|品名表記ゆれを正規化する設計]]も参照する。
