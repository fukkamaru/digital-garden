以下に、チャット開始時の **Canva Code 2.0の検証** から、**Figmaへの移行、`.fig`保存、SVGをAIとの受け渡し形式として使う方針、SVGエクスポート設定** までを、後からそのまま参照できる形で整理します。

# Canva Code 2.0 → Figma → SVGを使ったデザインワークフローの整理

## 1. 今回やりたかったこと

出発点は、HTMLで作成したサムネイルデザインを、コードを直接編集するのではなく、CanvaやFigmaのようなGUI上で編集できないか、という検討だった。  
想定していた作業は次のようなもの。

- AIにHTML/CSSでサムネイルの初期デザインを作らせる
- HTMLをブラウザで表示して完成イメージを確認する
- そのHTMLをデザインツールへ読み込む
- テキスト、画像、図形などを個別レイヤーとして扱う
- マウスで位置、サイズ、色、フォント等を微調整する
- 必要に応じてテキストボックスや図形も新規追加する
- 編集後も、AIが構造を理解しやすい形式で残したい  
    特に最後の点が重要で、単なるPNG/JPEGではなく、**AIが座標・文字・階層・色などを機械的に理解できるデータを残したい**という考えがある。

---

## 2. Canva Code 2.0を試した結果

### Canva Codeの起動

Canvaホーム画面中央付近の「コード」からCanva Codeを起動した。  
HTMLファイル自体のアップロードには成功した。

### 3840×2160 HTMLのサイズ問題

元のサムネイルHTMLは、

```text
3840 × 2160 px
16:9
```

で設計されていた。

ところがCanva Codeへ読み込むと、3840×2160の固定キャンバスとして扱われず、**縦長のCodeページ／レスポンシブコンテナのような形状へ強制的に変更された**。  
その結果、

- 右側が切れる
- スクロールバーが出る
- 元HTMLの3840×2160固定レイアウトが維持されない  
    という問題が発生した。

### 「先に3840×2160キャンバスを作る」方法も失敗

無料版では既存デザインのリサイズが有料だったため、

1. Canvaで新規に3840×2160の固定キャンバスを作成
2. その中へHTMLをアップロード  
    という回避策も試した。  
    しかしHTMLを選択した時点で、Canva側が再びCanva Code用ページへ切り替え、**3840×2160キャンバスを維持したままHTMLを配置することはできなかった**。  
    したがって、

> 3840×2160 Canvaデザインを先に作る → HTMLをその中へ入れる  
> という方法では解決しなかった。

## 3. Canva Codeの「編集」が何を意味するのか

Canva Code上には、

- 「Canva AIに聞く」
- 「編集」
- 「コードを生成」  
    などのメニューがあった。

### 「コードを生成」

「コードを生成」を押すと、左側にHTMLらしきコードが表示された。  
ただし内容は単純な元HTMLではなく、

```html
<!doctype html>
<html lang="ja">
<head>
<script>
window["__codeletBootstrap__"] = JSON.parse(...)
```

のような、Canva内部のCodelet実行用コードだった。  
またUIはコードエディターではなく「コードをコピー」となっていた。  
したがって、

> 「コードを生成」＝HTMLを直接編集する機能  
> ではなく、  
> Canva Code内部の作品から実行用コードを生成・表示する機能  
> と判断した。

### 元サムネイルHTMLでは「編集」がほぼ機能しなかった

元のサムネイルHTMLで「編集」を押すと、

- 画面がグレースケールになる
- 各要素を普通のCanvaオブジェクトとして選択できない  
    という状態になった。

そこで非常に単純なテストHTMLを作成した。

```html
<!doctype html>
<html>
<body>
  <h1>テスト見出し</h1>
  <p>テスト文章</p>
  <button>ボタン</button>
</body>
</html>
```

これをCanva Codeへ読み込むと、

- 見出しを選択できる
- テキストを書き換えられる
- フォント変更
- 色変更
- 太字等の文字装飾  
    が可能だった。

つまりCanva Code 2.0自体の編集機能は動作していた。

---

## 4. それでもCanva Codeが今回の用途に使えなかった理由

単純HTMLでは編集できたものの、実際に欲しかった「通常のデザイン編集」はできなかった。  
確認できたのは主に、

- 既存テキストの書き換え
- フォント変更
- 文字色変更
- 一部文字装飾  
    程度だった。

一方、必要としていた、

- 要素をドラッグして位置調整
- テキストボックスを新規追加
- 四角形、帯、線などの図形を追加
- 自由なリサイズ
- 画像を新規配置
- レイヤー順変更
- グループ化  
    などはできなかった。

したがってCanva Code 2.0の「編集」は、

> コードで作られた要素の一部プロパティをGUIから変更する  
> ための機能であり、  
> HTMLを通常のCanvaレイヤーへ変換して自由に編集する  
> 機能ではないと判断した。

### Canva Codeについての最終評価

今回の目的に対しては、  
**Canva Code 2.0は不採用**。  
HTMLを読み込ませること自体はできるが、サムネイル制作の仕上げ用GUIとしては編集自由度が足りない。

# 5. 他の候補を比較

Canva Codeが用途に合わなかったため、

- Figma
- PowerPoint
- SVG → Figma
- SVG → Canva
- SVG → Inkscape  
    などを比較した。

優先順位としては、

```text
1. HTML → Figma
2. HTML → SVG → Figma / Inkscape
3. HTML → PowerPoint
4. Canva系
```

となった。

### PowerPoint

PowerPointは、

- テキストボックス
- 写真
- 四角形
- 帯
- 線  
    などの編集には十分使える。  
    特に会社内で他の社員も修正する場合には扱いやすい。  
    ただしHTML/CSSをPowerPointオブジェクトへ直接正確に変換するには、座標・CSS等をPowerPoint図形へマッピングする処理が必要になる。  
    そのため今回の用途ではFigmaより優先度を下げた。

### SVG

SVGは、

- XMLベースのテキスト形式
- 座標
- 色
- テキスト
- 図形
- 画像参照  
    などを保持できるため、AIとのデータ交換形式として有力。  
    特に、

```xml
<text x="220" y="450" font-size="180" fill="#123DA5">
  塗る
</text>
<rect x="200" y="600" width="1500" height="180" fill="#123DA5"/>
```

のような構造であれば、AIが画像から推測する必要がなく、

- 「塗る」という文字
- X/Y座標
- フォントサイズ
- 色
- 帯のサイズ  
    などを直接理解できる。

# 6. FigmaでHTMLを読み込んだ結果

Figmaアカウントを作成し、FigmaのChrome拡張機能を利用した。

基本フローは、

```text
HTML
↓
Chromeで表示
↓
Figma Chrome拡張
↓
Figmaへキャプチャ
↓
編集可能レイヤー化
```

となる。

### ローカルHTMLのアクセス設定

最初は、

> To capture local files, enable this setting on Figma's Chrome extension page

というエラーが表示された。

Chrome拡張機能設定で、  
**「ファイルのURLへのアクセスを許可する」**  
をONにすることで解決した。

### 実際の結果

FigmaではHTMLの読み込みが非常に簡単に成功した。  
さらに重要だったのが、**HTMLの構造をかなり維持したままレイヤー化されたこと**。  
そのため、

- どのレイヤーが見出しか
- どれが背景か
- どれが帯か
- どれが画像か  
    という対応関係が分かりやすかった。

Canva Codeとは違い、

- マウスで移動
- サイズ変更
- テキスト編集
- 図形追加
- その他通常のデザイン編集  
    が可能。

### 現時点での結論

今回の用途については、

> **HTML → Figma**

が最も実用的。

# 7. Figmaのファイル保存について

会社で利用する場合でも費用を抑えたいという前提があり、無料のStarterプランを中心に検討した。

Figmaでは、

**File → Save local copy**

から `.fig` 形式でローカル保存できる。

実際に、

- `.fig` ダウンロード
- `.fig` 再インポート  
    の両方が問題なくできることを確認した。

### `.fig` の位置付け

`.fig` は単なる画像ではなく、**Figmaの編集可能な状態を保持するネイティブ保存形式**。

したがって、

```text
thumbnail.fig
```

を保存しておけば、後日Figmaへ再インポートして、

- テキスト変更
- 移動
- リサイズ
- レイヤー編集  
    などを継続できる。

つまり最低限、

> Figma内のファイル数制限に依存せず、必要な案件だけFigmaへ出し入れする

という運用が可能。

---

# 8. なぜHTMLでの保存も考えたのか

HTML出力について関心があった理由は、単なる保存形式の問題ではなかった。

本質的には、

> **AIへ渡すなら完成画像よりHTMLの方がAIファーストなのではないか**

という考えだった。

これは重要な視点。

PNG/JPEGしかない場合、AIは、

- この文字はここにある
- この帯は青い
- この写真は右側にある  
    と視覚的に推測する必要がある。

一方HTMLなら、

```html
<section class="headline">
  <span class="keyword">塗る</span>
  <span>すべり止め材</span>
</section>
```

さらにCSSで、

```css
.headline {
  position: absolute;
  left: 240px;
  top: 310px;
}
.keyword {
  font-size: 180px;
  color: #123da5;
}
```

のように、

- 意味
- 階層
- 座標
- サイズ
- 色
- フォント  
    を明示できる。

そのため、**AIに理解・修正させるデータとしてはPNG/JPEGよりHTMLの方が優秀**。

# 9. Figmaを挟むことで発生する「HTMLの陳腐化」

一方で、

```text
AI
↓
HTML
↓
Figma
↓
人間がFigmaで修正
```

と進むと問題が発生する。

例えばFigma上で「塗る」を左へ40px動かしても、元HTMLは更新されない。

つまり、

```text
元HTML = 古い状態
Figma = 最新状態
PNG = 最新状態
```

となる。

したがって、  
**Figma編集後の最新デザインをAIへどう返すか**  
が次の課題になった。

# 10. そこでSVGを使う

このタイミングでSVGを活用する方針になった。

役割を明確にすると、

|形式|役割|
|---|---|
|HTML|AIが最初にデザインを生成する入口|
|`.fig`|人間がFigmaで編集するマスターデータ|
|SVG|Figma編集後の状態をAI・他ソフトへ渡す交換形式|
|PNG/JPG|完成確認・公開・納品用|

つまり、

```text
AI
↓
HTML
↓
Chrome
↓
Figma
↓
人間がGUI編集
↓
.fig ── 人間のマスター
↓
SVG ── AIへの受け渡し
↓
AI
```

という循環を作る。

### HTMLとSVGの役割の違い

HTMLは、

- AIによる初期生成
- レイアウト設計  
    に向いている。

SVGは、

- 人間がFigmaで修正した「最新状態」をAIに返す
- Figma以外のInkscape等へ渡す  
    用途に向いている。

したがって、

> HTMLを最終保存形式にする必要はない  
> という整理になった。

# 11. 推奨ファイル構成

各サムネイル案件については、次のような構成が合理的。

```text
thumbnail/
├─ thumbnail.html
├─ thumbnail.fig
├─ thumbnail.svg
├─ thumbnail.png
└─ assets/
   ├─ main-photo.jpg
   ├─ texture.jpg
   └─ product.png
```

役割は、

- `thumbnail.html`
    - AIが作成した初期設計
- `thumbnail.fig`
    - Figma編集後の本体
    - 人間による再編集用マスター
- `thumbnail.svg`
    - AI・Inkscape・その他ツールへの交換形式
- `thumbnail.png`
    - 完成状態確認用
- `assets/`
    - 実素材原本

となる。

# 12. Figma → SVGエクスポート設定

FigmaからSVGを書き出す際、今回の用途は一般的な納品SVGとは少し違う。

目的は、

> **AIが構造を理解しやすく、可能な限り再編集性も残すSVG**

を作ること。

推奨設定は次の通り。

|項目|推奨|
|---|---|
|サフィックス|なし|
|カラープロファイル|**sRGB（ファイルと同じ）**|
|重なり合うレイヤーを無視する|**ON**|
|バウンディングボックスを含める|**OFF**|
|`"id"`属性を含める|**ON**|
|テキストをアウトライン化|**OFF**|

### `"id"`属性を含める → ON

これはAIとの連携を考える上で重要。

Figmaのレイヤー名がSVGのIDとして利用されやすくなるため、

```xml
<g id="MainPhoto">
...
</g>
<text id="MainHeadline">
...
</text>
<rect id="SubtitleBand">
...
</rect>
```

のような意味のある構造を残せる。

そのためFigma側でも、

- `MainPhoto`
- `MainHeadline`
- `Keyword`
- `SubtitleBand`
- `TexturePhoto`  
    など、意味が分かるレイヤー名を付ける価値がある。

### 「テキストをアウトライン化」→ OFF

これは特に重要。

ONにすると、

```text
「塗る」
```

という文字が、文字情報ではなくベクターパスへ変換される。

見た目は維持されるが、

- AIが文字として理解しにくくなる
- Inkscape等でテキスト編集できなくなる
- SVG→Figma再インポート時にも文字として扱いにくい  
    というデメリットがある。

今回のAI連携用途では、**必ずOFFを基本とする**。

# 13. カラープロファイルの考え方

FigmaのSVGエクスポートでは、

- sRGB（ファイルと同じ）
- sRGB
- Display P3  
    が選択できる。

今回の推奨は、

> **sRGB（ファイルと同じ）**

ただし前提として、Figmaファイル自体もsRGBで運用する。

### sRGB

Web・Windows・ブラウザ・YouTube・一般的な画像ツールで最も互換性が高い標準的なRGB色空間。

今回の用途は、

```text
HTML
→ Chrome
→ Figma
→ SVG
→ AI
→ 他ソフト
→ YouTube
```

なので、sRGBとの相性がよい。

### Display P3

sRGBより広い色域を扱える。  
特に非常に鮮やかな、

- 赤
- 緑
- オレンジ
- シアン  
    などを表現しやすい。

一方で、

- P3非対応環境
- 一部ソフト
- 他ツールとのデータ交換  
    を考えると、今回の用途では互換性面のメリットが小さい。

そのためYouTubeサムネイルとAI連携では、P3を積極的に使う必要はない。

### 「sRGB（ファイルと同じ）」と「sRGB」

現在のFigmaファイルがsRGBなら、結果は基本的に同じ。

違いは将来FigmaファイルをDisplay P3に変更したとき。

```text
Figmaファイル = Display P3
```

なら、

- 「ファイルと同じ」→ Display P3で出力
- 「sRGB」→ sRGBへ変換して出力  
    となる。

したがって運用としては、

```text
Figmaファイル = sRGB
SVGエクスポート = sRGB（ファイルと同じ）
```

に統一するのがシンプル。

# 14. 現時点での標準ワークフロー案

今回の検証を踏まえると、サムネイル制作は次の流れがかなり合理的。

```text
① 制作ブリーフ
    ↓
② AIがHTML/CSS生成
    ↓
③ Chromeで表示確認
    ↓
④ Figma Chrome拡張で取り込み
    ↓
⑤ HTML構造を維持したレイヤーとしてFigma化
    ↓
⑥ 人間がFigmaでGUI調整
    ・位置
    ・サイズ
    ・テキスト
    ・画像
    ・図形
    ・色
    ↓
⑦ .fig保存
    └─ 人間向け編集マスター
    ↓
⑧ SVG保存
    └─ AI・他ソフトへの受け渡し
    ↓
⑨ PNG/JPG書き出し
    └─ 完成成果物
```

AIへ再度修正を依頼する場合は、

```text
Figma
↓
SVG
↓
AI
↓
必要に応じて新HTMLまたは修正版設計
↓
Figma
```

という循環も可能。

# 15. 今回の重要な判断

最終的に大きく整理すると次の通り。

- **Canva Code 2.0**
    - HTMLの表示自体は可能
    - 一部文字編集も可能
    - しかし通常のデザイン編集には不十分
    - 今回の用途では不採用
- **Figma**
    - HTMLから編集可能なレイヤーへ変換できた
    - HTML構造もある程度維持される
    - GUI編集が容易
    - 今回の用途の本命
- **`.fig`**
    - 人間が再編集するためのマスターファイル
    - ダウンロード・再インポートとも確認済み
- **HTML**
    - AIに初期デザインを生成させる形式として非常に有効
    - ただしFigma編集後は最新状態ではなくなる
- **SVG**
    - Figmaで人間が修正した最新状態をAIへ返す中間形式として活用
    - AIファーストな交換形式として有力
- **PNG/JPEG**
    - 完成確認には必要
    - ただしAIに構造を引き継ぐ形式としては補助的
- **カラープロファイル**
    - sRGBで統一
    - SVGは「sRGB（ファイルと同じ）」を基本とする
- **SVGの文字**
    - アウトライン化しない
    - テキスト情報を保持する
- **SVGのID**
    - `"id"`属性を含める
    - Figmaのレイヤー名を意味のある名前にしてAI理解を補助する

## 現時点の役割分担を一言でまとめると

```text
HTML = AIが作る
Figma = 人間が仕上げる
.fig = 人間向けマスター
SVG = AIへ戻す
PNG/JPG = 完成物
```

この構成が、今回の検証結果から最も自然な形になっています。
