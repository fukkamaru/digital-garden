結論として、この6語は「何のためのものか」と「どの状態にあるか」で使い分けると明確です。

- `dummy / mock / sample / test`：主に用途・役割を表す
- `temp / draft`：主に保存期間・完成状態を表す

そのため、`draft-design` や `test-data` のように、対象物と組み合わせて命名するのが基本です。

|単語|中心的な意味|適した場面|例|
|---|---|---|---|
|`dummy`|中身や機能を持たない代用品|仮データ、仮商品、穴埋め|`dummy-user`、`dummy-product`|
|`mock`|本物らしく見せた再現物|UI見本、サービス画面、外部システムの模倣|`mock-screen`、`mock-api`|
|`sample`|参考として見せる代表例|記入例、コード例、コンテンツ例|`sample-config`、`sample-article`|
|`test`|正しさを検証するためのもの|動作確認、品質確認、自動テスト|`test-data`、`test-account`|
|`temp`|短期間だけ使用するもの|一時保存、中間生成物、作業用コピー|`temp-image`、`temp-export`|
|`draft`|未完成で、今後修正されるもの|原稿、企画、設計、デザインの制作途中|`draft-proposal`、`draft-design`|

## それぞれの違い

### `dummy`：本物の代わりに置く

本物である必要がなく、場所や形式だけ満たせばよいものです。

- 名前欄を埋めるための架空ユーザー
- ECサイトに配置する仮の商品
- レイアウト確認用の仮テキスト
- 接続されていないダミーボタン

```
dummy-user
dummy-product
dummy-content
```

「正しい動作を検証する」というより、**そこに何かを置いておく**ことが目的です。

なお、人物や顧客を指して `dummy customer` とすると雑に聞こえる場合があります。対外的な文章では `placeholder` や `example` のほうが無難です。

---

### `mock`：本物らしく再現する

見た目や振る舞いを、本物に近い形で再現したものです。

デザインでは：

- `mockup`：完成イメージに近い静的な見本
- `screen mock`：画面の見本
- `device mockup`：端末にはめ込んだ表示イメージ

システム開発では：

- `mock API`：本物のAPIの代わりに応答する仕組み
- `mock service`：外部サービスを模倣したもの
- `mock object`：依存先の振る舞いを模倣するテスト用オブジェクト

```
mock-payment-api
homepage-mockup
mock-response
```

`dummy` よりも、**本物らしい外観や振る舞いが必要**な場合に使います。

---

### `sample`：参考になる実例

他の人が見て、理解したりコピーしたりするための例です。

- サンプルコード
- 設定ファイルの記入例
- 記事の完成例
- 商品サンプル
- データセットの一部

```
sample-config.yaml
sample-article.md
sample-request.json
```

`dummy` との違いは、`sample` には通常、**参考として役立つ内容**が求められる点です。

たとえば：

- `dummy-data`：画面を埋められればよい
- `sample-data`：実際の構造や使い方を理解できる
- `test-data`：特定の条件を検証できる

---

### `test`：検証するために使う

正しく動くか、期待する結果になるかを確認するためのものです。

- テスト用アカウント
- テストデータ
- テスト環境
- テストケース
- テスト配信

```
test-account
test-dataset
test-environment
```

`sample` は説明・参考が目的ですが、`test` は**合否や動作の確認**が目的です。

本番環境に混ざると事故につながるため、`test` は命名だけでなく、環境や権限も分離するのが安全です。

---

### `temp`：使用後に消してよい一時物

完成度ではなく、寿命の短さを表します。

- 変換処理の途中で生成した画像
- 一時的な書き出しファイル
- コピー＆ペースト用の作業メモ
- 一時アップロード先

```
temp-export.csv
temp-render.png
temp-upload/
```

`draft` との違いは重要です。

- `temp`：役目が終われば削除する
- `draft`：修正を重ねて完成版にする

つまり、長期間育てる原稿を `temp` と呼ぶのは適切ではありません。

---

### `draft`：完成に向けて編集中

公開・承認・納品前の制作物です。

- 記事の下書き
- 提案書の初稿
- UIデザインの制作途中
- 要件定義の草案
- メールの下書き

```
draft-article.md
proposal-draft.docx
draft-design.fig
```

`draft` は将来的に正式版になる可能性があります。バージョンを表す場合は、次のような名前が分かりやすいです。

```
proposal-draft-v01
proposal-review-v02
proposal-final
```

ただし `final-v2-final` のような名前になりやすいため、管理システムがある場合はファイル名よりステータスや履歴で管理するほうが確実です。

## 分野別の推奨例

|分野|状況|推奨語|
|---|---|---|
|システム|外部APIを模倣する|`mock`|
|システム|テスト条件を再現するデータ|`test`|
|システム|値が必要なだけの代用品|`dummy`|
|システム|利用者向けコード例|`sample`|
|デザイン|完成イメージの見本|`mock` / `mockup`|
|デザイン|制作途中のデザイン|`draft`|
|デザイン|配置確認だけの仮素材|`dummy` / `placeholder`|
|サービス|社内検証用アカウント|`test`|
|サービス|デモで見せるデータ|`demo` / `sample`|
|コンテンツ|完成例として見せる記事|`sample`|
|コンテンツ|執筆途中の記事|`draft`|
|ファイル処理|後で削除する中間ファイル|`temp`|

## 迷ったときの判断基準

次の質問でほぼ判別できます。

1. 本物の代わりに場所を埋めるだけか  
    → `dummy`
    
2. 本物の見た目や振る舞いを再現するか  
    → `mock`
    
3. 他人が参考にする例か  
    → `sample`
    
4. 正しく動くか検証するためか  
    → `test`
    
5. 役目が終われば削除するか  
    → `temp`
    
6. 修正を重ねて完成させるか  
    → `draft`
    

補足すると、実務では `placeholder`、`prototype`、`demo` もよく使います。

- `placeholder`：後で正式な内容に差し替える仮置き
- `prototype`：アイデアや操作性を検証する試作品
- `demo`：人に機能や価値を見せる実演用
- `staging`：本番公開前に統合確認する環境

特にデザインでは、仮画像は `dummy-image` より `placeholder-image`、操作検証できる試作品は `mock` より `prototype` のほうが意図を正確に表せます。
