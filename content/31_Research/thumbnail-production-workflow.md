# サムネイル制作ワークフロー整理

## 1. 現在のサムネイル制作の考え方

現在のサムネイル制作では、単純に「AIにサムネイル画像を生成させる」のではなく、AIとの対話を使ってデザインそのものを設計している。  
主にAIとの対話で詰める内容は次の通り。

- 何を最も強く訴求するか
- メインコピー・サブコピーの優先順位
- どの写真をメインに使うか
- 写真のトリミングや配置
- 配色
- 余白
- 視線誘導
- 装飾
- 画像の役割
- 誤解を招く表現がないか  
    これまでは、こうして決めた内容をHTML形式の設計書に落とし込み、その設計書をAIに読ませて完成サムネイルを生成させる方式を使ってきた。  
    一方で今後は、AIに設計書を再解釈させて画像を生成させるのではなく、**HTML自体を完成サムネイルのレイアウトとして使う方式**も検討している。

## 2. 「設計書→AI生成」と「HTML完成型」の比較

検討した方式は大きく2つある。

### 方式A：HTML設計書をAIに読ませて完成画像を生成

流れ：  
AIとの対話  
→ デザイン決定  
→ HTML設計書  
→ AIがHTMLを解釈  
→ 完成画像生成  
メリット：

- AIによる写真の再構成ができる
- デザインに偶発的な良さが出る可能性がある
- 実際には存在しない構図も作れる  
    デメリット：
- AIが設計を毎回再解釈する
- 座標や余白が完全には固定されない
- 文字崩れや誤字の可能性がある
- 同じ設計でも出力に差が出る
- 修正のたびに再生成が必要になる
- 同シリーズを量産するときの再現性が低い

### 方式B：HTMLに必要画像を読み込めば完成

流れ：  
AIとの対話  
→ デザイン決定  
→ HTML/CSSとしてレイアウトを固定  
→ 指定場所に素材画像を読み込む  
→ 完成  
メリット：

- レイアウトが完全に固定できる
- 文字が正確
- 同シリーズを量産しやすい
- 素材差し替えだけで再利用できる
- ブランドやシリーズの統一感を維持しやすい
- AIによる再解釈が入らない
- 修正箇所が明確  
    デメリット：
- 写真そのものの大胆な再構成には弱い
- HTML/CSSで表現できる範囲に依存する  
    この比較から、**完成形の制作工程としては方式Bの「HTML完成型」の方が向いている**という結論になった。

## 3. AIとHTMLの役割分担

AIを完全に外すのではなく、役割を分ける考え方が適切。

### AIが担当する部分

- コンセプト設計
- サムネイル構成の検討
- コピー案
- 写真の選定
- 配色検討
- レイアウト案
- 必要に応じて背景・加工素材・補助画像などの生成

### HTMLが担当する部分

- 文字
- ロゴ
- 枠
- 見出し
- バッジ
- 配色
- 余白
- グリッド
- 写真位置
- 写真サイズ
- クロップ領域
- レイヤー順
- 最終レイアウト  
    基本的な考え方は、  
    **画像の中身を作る・考える → AI**  
    **画像をどこにどう配置するか → HTML**  
    とする。  
    HTMLを「AI向けの設計書」としてだけ使うのではなく、**そのHTMLをブラウザで開けば完成サムネイルが表示される状態**まで持っていく。

## 4. HTMLの役割は増やさない

HTML完成型を採用する場合でも、HTMLに保存処理まで組み込む案は採用しない。  
例えば、

- 「PNG保存」ボタン
- html2canvasなどのライブラリ
- 書き出し用JavaScript
- ダウンロード機能  
    などをHTML側に追加する方法も考えられるが、これは採用しない。  
    理由は、HTMLに別の意味や責務を持たせたくないため。  
    HTMLはあくまで、  
    **「サムネイルを正しく表示する」**  
    ことに専念させる。  
    画像保存・書き出しはHTMLの外側の仕組みで行う。  
    この役割分担を維持する。

```text
HTML
↓
完成サムネイルを表示

Chrome / DevTools
↓
PNGとして書き出す
```

将来この操作が面倒になった場合も、HTML側に機能を追加するのではなく、**Chrome拡張機能として外部化する方向**を優先する。

## 5. サムネイルの出力サイズ

当初「3820×2160だったか」と確認したが、正しくは、  
**3840 × 2160 px**  
である。  
これは16:9の4K UHD解像度。  
今後HTMLでサムネイルを作る場合、完成サムネイルのルート要素自体を、

```css
width: 3840px;
height: 2160px;
```

として設計する。  
つまり、画面に見えているサイズを拡大して保存するのではなく、**最初から3840×2160の完成物をHTML上に存在させる**。

## 6. Chrome DevToolsでPNG保存する方針

HTMLから完成サムネイルを保存する方法として、Chrome DevToolsを使う方針に決定した。  
主に利用する機能は、  
**Capture node screenshot**  
である。  
これは、Webページ全体ではなく、Elementsパネルで選択しているDOM要素だけをPNGとして保存する機能。  
基本的な操作は次の通り。

1. ChromeでHTMLを開く
2. サムネイル上で右クリック
3. 「検証」を選択
4. DevToolsのElementsパネルを開く
5. サムネイル全体を囲むHTML要素を選択
6. その要素を右クリック
7. 「Capture node screenshot」を実行
8. PNGとして保存される  
    例えばHTMLが、

```html
<body>
  <div id="thumbnail">
    ...
  </div>
</body>
```

となっている場合、選択するのは、

```html
<div id="thumbnail">
```

である。

## 7. 「Capture full size screenshot」との違い

DevToolsには、  
**Capture full size screenshot**  
という別の機能もある。  
これはWebページ全体をキャプチャする機能。  
今回必要なのは、  
**3840×2160のサムネイル部分だけ**  
なので、基本的には使用しない。  
使用するのは、  
**Capture node screenshot**  
とする。

## 8. 現在発生している問題

実際にCapture node screenshotを試したところ、  
**サムネイル部分だけでなく、ブラウザ全体の背景・余白まで一緒に画像として保存される**  
という問題が発生した。  
考えられる原因は、サムネイル本体ではなく、

- `<body>`
- `<main>`
- 外側のラッパー
- プレビュー領域全体  
    などを選択していること。  
    Capture node screenshotは、選択中のDOMノードそのものをキャプチャするため、外側の要素を選べば背景や余白も含まれる。

## 9. HTML構造として望ましい形

DevToolsで安定して書き出すためには、HTML上で、  
**サムネイル本体**  
と  
**ブラウザ上のプレビュー領域**  
を明確に分離した方がよい。  
例えば、

```html
<body>
  <main id="thumbnail">
    <!-- サムネイル全体 -->
  </main>
</body>
```

CSS：

```css
#thumbnail {
  width: 3840px;
  height: 2160px;
}
```

とする。  
この場合、

- `body` = ブラウザ上の表示・プレビュー領域
- `#thumbnail` = 実際にPNG化する完成物  
    という役割分担になる。  
    重要なのは、**3840×2160の完成サムネイル全体を必ず1つのルート要素で囲むこと**。  
    これによって毎回同じ要素を選択して書き出せる。

## 10. DevToolsで対象要素を見分ける方法

サムネイル上で右クリック→「検証」を行った場合、最初からサムネイル全体が選択されるとは限らない。  
例えば、

```text
<img>
↓
<div class="photo">
↓
<div class="photo-area">
↓
<div id="thumbnail">
```

のように、画像や文字など内部要素が選択される場合がある。  
その場合はElementsパネルで親要素を順番にたどり、**サムネイル全体だけを囲っている要素**まで上がる。  
ElementsパネルでDOM要素にマウスを乗せると、ブラウザ上でその要素の範囲がハイライトされる。  
そのハイライトが、  
**3840×2160のサムネイル部分だけ**  
になっていることを確認してからCapture node screenshotを実行する。

## 11. DPRについて

3840×2160のHTML要素をキャプチャした場合でも、環境によってはDevice Pixel Ratio（DPR）の影響で、

- 3840×2160  
    ではなく、
- 7680×4320  
    などになる可能性がある。  
    そのため、最初に保存したPNGについてはWindowsのプロパティなどで実際のピクセル数を確認する。  
    必要であればDevToolsのDevice ToolbarからDPR=1に設定する。  
    ただし、まずは設定を変更せず、  
    **3840×2160のルート要素 → Capture node screenshot**  
    で正しいサイズになるか確認する。

## 12. 将来的なChrome拡張機能

Chrome DevToolsでの手動操作が面倒になった場合は、HTMLを変更するのではなくChrome拡張機能として書き出し処理を外部化する。  
想定できる処理は、

- 開いているHTMLから`#thumbnail`を検出
- 対象要素だけをキャプチャ
- 3840×2160で保存
- ファイル名を自動設定
- 必要に応じてPNG/JPEGを選択  
    など。  
    ただし、現段階ではChrome拡張機能を作る必要はなく、まずDevToolsによる手動運用で十分。

## 13. 現時点での確定方針

現時点の方針は次の通り。

- サムネイルの企画・デザイン検討にはAIとの対話を使う
- 最終レイアウトはHTML/CSSで固定する方向を重視する
- HTMLに素材画像を読み込めば完成状態になる構成を目指す
- HTMLには画像保存機能を追加しない
- HTMLはサムネイルの表示・レイアウトに専念させる
- サムネイルの基本出力サイズは3840×2160px
- 完成PNGの書き出しにはChrome DevToolsを使用する
- 基本的にCapture node screenshotを使う
- Capture full size screenshotは使用しない
- サムネイル全体を1つのルート要素で囲む
- `body`とサムネイル本体を分離する
- DevToolsではサムネイル本体のルート要素だけを選択する
- 書き出し作業が将来煩雑になったらChrome拡張機能として外部化する
- 保存機能をHTML側へ持ち込まない

## 14. 現在の未解決事項

現在確認すべき点は主に次の2点。

- 今使っているHTMLで、サムネイル本体だけを囲っているDOM要素がどれか
- Capture node screenshotで実際に3840×2160のPNGが出力されるか  
    特に現在は、**サムネイル以外のブラウザ背景まで保存される問題**が残っている。  
    次に確認する場合は、実際に使用しているHTMLを見れば、  
    「どの要素をCapture node screenshotすればよいか」  
    「HTML構造を修正する必要があるか」  
    を具体的に判断できる。
