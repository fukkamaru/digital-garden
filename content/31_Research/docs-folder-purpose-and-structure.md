# docsフォルダの役割と構成例

`docs` は、プロジェクトや製品を理解・運用するための文書を集める入口である。ただし、リポジトリ内の技術文書なのか、組織の共有フォルダなのかで、置くべき内容と公開範囲は変わる。名称だけで用途を決めず、読者・責任者・公開範囲を先に決める。

## 置く文書を役割で分ける

|役割|主な文書|
|---|---|
|プロジェクト運営|要件定義、仕様、設計、計画、意思決定記録、議事録|
|利用者支援|マニュアル、導入ガイド、操作手順、FAQ、トラブルシューティング|
|開発・運用|環境構築、アーキテクチャ、API・データ構造、デプロイ、障害対応|
|調査・報告|調査レポート、分析結果、参考資料、定期報告|
|再利用素材|テンプレート、フォーム、チェックリスト、記入例|

## 構成例

```text
docs/
├─ README.md
├─ getting-started/
├─ guides/
├─ reference/
├─ architecture/
├─ operations/
├─ decisions/
└─ assets/
```

- `README.md`：全体の入口、対象読者、更新方法を示す。
- `getting-started/`：導入時に必要な最初の手順を置く。
- `guides/`：目的別の操作・作業ガイドを置く。
- `reference/`：仕様や参照情報を置く。
- `architecture/`：設計と構造を説明する。
- `operations/`：運用・保守・障害対応を扱う。
- `decisions/`：重要な判断と理由を残す。
- `assets/`：文書から参照する画像などを置く。

## 設計時の確認

1. 誰が読むか。公開用か、組織内限定か。
2. 文書の責任者と更新方法が決まっているか。
3. ソースコードと同じ履歴で管理すべきか。
4. 既存の保存場所と重複しないか。
5. 機密情報・個人情報を含まないか。

契約書、NDA、個人情報、認証情報は、アクセス制御のない公開リポジトリの`docs`には置かない。権限管理と保存期間を設定できる保管場所を使う。

`docs`を作るだけでは情報は維持されない。入口、分類規則、更新責任、古い文書の扱いを合わせて決めることで、あとから参照・保守できる構成になる。
