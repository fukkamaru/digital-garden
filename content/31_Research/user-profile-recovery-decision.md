# ユーザープロファイルを復旧するか、諦めるかの判断基準

このノートは「旧プロファイルを復旧する」か「旧プロファイルを残して別の正常環境へ必要なデータだけ移す」かを判断するためのものだ。CF-LV事例では、後者を選ぶ判断に変わった。経緯と実行した修復操作は[Windowsユーザープロファイル障害・SSD不良ブロック調査まとめ](windows-profile-ssd-read-errors.md)を正本とする。

「諦める」は旧データを捨てる意味ではない。壊れた可能性のあるプロファイルを本番環境として復活させる試みを止め、必要なデータの救出・保全へ目的を切り替えることを指す。

## 判断表

|確認事項|復旧を一度検討できる条件|新しい環境へ移す判断を強める条件|
|---|---|---|
|原因の範囲|`.bak`などSIDとパスの対応だけが明確に崩れており、元プロファイルのファイルを正常に読める|`NTUSER.DAT`やAppDataの読めない・破損した記録がある|
|ストレージの状態|Disk系エラーがなく、必要なファイルを安定して読める|I/Oエラー、CRCエラー、Event ID 7の反復などがある|
|データ保全|バックアップ未完了で、まず読める範囲の救出が必要|必要なデータを別媒体に保全し、開けることまで確認できた|
|旧環境への依存|移しにくい証明書・アプリ設定があり、原因が限定できる|メール・共有・アプリを再設定でき、必要なデータを選択的に移せる|
|再発時の影響|安全な媒体上で検証できる|同一の疑わしいストレージ上で再構築することになる|

Microsoftも、破損したプロファイルについて新しい管理者アカウントを作り、旧ユーザーフォルダからファイルをコピーする手順を案内している。ただし、メールやアプリは別途再設定・再インポートが必要になり得る。[破損したユーザープロファイルを修復する（Microsoft Support）](https://support.microsoft.com/windows/security/identity-signin/fix-a-corrupted-user-profile)

## CF-LV事例で判断が変わった理由

当初は、`ProfileList`の`.bak`と`State`を直せば元の`user`プロファイルを戻せる可能性を検討した。そのため、レジストリをバックアップし、独立した`repairadmin`から一度だけ修復を試した。

しかし、再ログオンで同じ失敗が再発し、8月19日の`NTUSER.DAT`のCRCエラーと、同時刻帯から翌日に継続するDisk Event ID 7が確認された。この時点で、問題は単純なSIDとフォルダの紐付けではなく、元プロファイルを読み出す土台のストレージに疑いがあると判断した。

```text
初期案: ProfileListを直す → userを復旧する
    ↓ 修復後も再発
追加の根拠: NTUSER.DATのCRCエラー + Disk Event ID 7の反復
    ↓
判断変更: 同一ストレージ上での復旧・新規本番環境の構築を中止
    ↓
優先順位: データ保全 → ストレージ・保守の判断 → 新しい環境で選択的に移行
```

## 移行時に持ち込まないもの

旧`C:\Users\user`をすぐ削除せず、バックアップと新環境での確認が済むまで保持する。一方で、次のものを丸ごと新規プロファイルへコピーしない。

- `NTUSER.DAT`、`NTUSER.DAT.LOG1`、`NTUSER.DAT.LOG2`
- AppData全体
- 古いProfileListのレジストリ設定
- TEMPプロファイル

戻す対象は、Desktop、Documents、Downloads、Pictures、業務ファイルを基本にする。アプリ固有の設定が必要な場合は、アプリを再インストールまたは再設定した後に、必要なデータだけを個別に確認して移す。

この事例では、同一ストレージ上の新規ユーザー作成は本番復旧策にしなかった。新しいストレージまたは別端末上に、正常な環境を用意してから移行することが前提になる。
