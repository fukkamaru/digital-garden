# ユーザープロファイル障害の原因調査に要した時間の評価

このノートは、Panasonic CF-LVで発生したユーザープロファイル障害について、原因候補をどこまで絞れたか、そこにどれほどの調査作業が必要だったかを振り返る記録である。障害の時系列、実際に行った操作、コマンド、ログ上の確認結果は、[Windowsユーザープロファイル障害・SSD不良ブロック調査まとめ](windows-profile-ssd-read-errors.md)を正本とする。

ここで述べる時間短縮効果は、この一事例の評価であり、再現可能な測定値ではない。

## もとの問いと評価

Fukkamaruは、AIも使いながら原因候補の特定までに業務のほぼ1日を使った。この時間は、単に検索結果を読む時間ではなく、実機の状態と複数の記録を照合する時間を含むため、不自然ではない。

今回の成果は「1日かかった」ことではなく、当初はユーザープロファイル障害に見えていた症状を、ストレージ読み取り障害の可能性が高いところまで切り分け、データ保全とPC交換を優先すべき状態だと判断できたことにある。

## 調査に必要だった作業

調査は、一つの既知手順をなぞるだけでは終わらなかった。次の確認を相互に結び付ける必要があった。

1. 症状を観察し、`%USERPROFILE%`でTEMPプロファイルになっていることを確認する。
2. User Profile Serviceの記録から、プロファイルのどのファイルをいつ読み込めなかったかを確認する。
3. 8月18日と19日の記録を比べ、正常に使えた状態から障害発生までの時系列を組み立てる。
4. SystemログのDisk Event ID 7について、発生回数と継続性を確認する。
5. `Harddisk0`という表記がHDDだけを指すわけではないこと、`chkdsk`が確認できる範囲を区別する。
6. 新しいアカウントで業務を継続できるか、同じストレージ上で環境を作り直してよいかを判断する。

特に難しかったのは、プロファイルの`.bak`状態だけを修復対象と見なさず、その下位にあるストレージ読み取り障害の可能性まで確認した点である。

## AIと人間の役割

AIは、検索語の候補、Microsoft資料の探索、イベントIDの意味の整理、次に確認する場所の提案を担った。一方で、実機のログ確認、画面操作、日時の突合、正常状態と異常状態の比較、業務を継続するか停止するかの判断は、Fukkamaruが担った。

したがって、AIを使っても数時間から1日規模になることはある。AIなしなら、ProfileListだけで修復を終えずSystemログまで確認し、Event ID 7とプロファイル障害を関連付け、`chkdsk`の役割とSSD交換判断を分けるまでに、さらに時間がかかった可能性が高い。

## 次回に再利用する順序

同種の症状に再遭遇した場合は、次の順で確認することで、原因候補をより早く絞れる可能性がある。

```text
症状の確認
  → %USERPROFILE% の確認
  → User Profile Serviceの記録
  → 同時刻帯のSystemログ
  → Disk / NTFS / WHEAなどの記録
  → データ保全と復旧方針の判断
```

ただし、この順序は原因を自動的に確定する手順ではない。ログの内容、端末の状態、データ保全の必要性を踏まえて、確認範囲と次の操作を決める。
