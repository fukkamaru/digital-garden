# Power Queryにおける結合キーの設計と管理

## このノートの位置付け

このノートは、Power Queryで売上データとマスタを結合するときの、結合キー、列名、集計後のキーの扱いを整理する資料である。データ層の全体像は[Kyoto Patty 029の架空事業設定とデータ設計](kyoto-patty-029-sample-business.md)を参照する。

結論だけでなく、どのパターンがあり、どの条件で選ぶかを残す。すべての処理で同じキーを使い続けることが目的ではなく、現在のテーブル粒度で必要な結合を安全に行うことが目的である。

## 基本原則

- Raw層では、元システムや受領データの列名と値をできるだけ維持する。
- Standard層では、分析に必要な名称、型、表記、結合キーを統一する。
- Analysis層では、集計粒度に必要なキーだけを残すか、新しく作る。
- Report層では、読み手に必要な場合を除き、`key_`列を出力しない。

```mermaid
flowchart LR
    A[Raw<br>元の列名・値] --> B[Standard<br>名称・型・key_列を統一]
    B --> C[Analysis<br>集計粒度に合うキーを保持・作成]
    C --> D[Report<br>必要な表示列だけを出力]
```

## マスタの列名をどう扱うか

販売システムの列名と、分析で使いたい列名が異なる場合を考える。

| 元システムの列名 | 分析で使いたい列名 |
| --- | --- |
| コード | 商品コード |
| 名称1 | 商品名 |
| 分類2 | 分類 |
| 分類1 | カテゴリー |

### パターンA：マスタ自体を分析用の列名にする

マスタの列を最初から`商品コード`、`商品名`、`分類`、`カテゴリー`のように管理する方法である。分析では読みやすいが、元システムと比較するときに、どの列を置き換えたか確認する必要がある。

### パターンB：Rawではシステム名を維持し、Standardで名前を変える

マスタ原本は`コード`、`名称1`、`分類2`、`分類1`のまま保持し、Power Queryで分析用の列名へ変換する方法である。元データとの対応を追いやすく、複数用途へ流用しやすい。

このノートでは、RawではパターンBを採用する。分析用の分かりやすい列名はStandard以降で使う。元システム自体が分析用の列名を正式採用している場合は、同じ名前を重ねて変換する必要はない。

## 結合キーを片側と両側のどちらに作るか

売上データと商品マスタを、`商品コード`で結合する例を考える。

### パターンA：片側だけに結合用の列を作る

片方がすでに正規化済みで固定され、もう片方だけに前処理が必要なら、加工側だけへ`key_商品コード`を作る方法で足りる。

| 売上データ | 商品マスタ |
| --- | --- |
| 商品コード | `key_商品コード` |
| 001 | 001 |

この方法は列を増やさずに済む。ただし、片側が本当に固定され、表記揺れや型の違いが起きないことを確認する必要がある。

### パターンB：両側に結合用の列を作る

両方のデータへ`key_商品コード`を作り、同じ変換を適用してから結合する方法である。

| 売上データ | 商品マスタ |
| --- | --- |
| 商品コード | 商品コード |
| `key_商品コード` | `key_商品コード` |
| 001 | 001 |

前後の空白除去、全角・半角の統一、大文字・小文字の統一、データ型の統一が必要な場合は、この方法が安全である。元の`商品コード`を残せるため、変換結果の検証もしやすい。

このノートでは、入力元の品質を保証できない場合はパターンBを採用する。`key_`という接頭辞は、元の値ではなく結合専用に整えた列であることを表す。

## 集計後にキーを残すか

キーは一度作ったら残し続けるものではない。グループ化後のテーブルが、どの粒度で再結合するかによって判断する。

| 状況 | 例 | 判断 |
| --- | --- | --- |
| 同じ粒度で再結合する | 商品別売上を、商品マスタへ再結合する | `key_商品コード`を残す |
| 粒度が変わる | 月別売上だけへ集計する | `key_商品コード`は削除し、必要なら`key_年月`を作る |
| 複数列の組み合わせが必要 | 得意先別・月別に再結合する | `key_得意先_年月`のような結合キーを作る |

重要なのは「以前のキーを維持するか」ではなく、「現在のテーブルを何と、どの粒度で結合するか」である。

## 推奨する処理の流れ

```text
Raw
  元の列名・値を保持
  ↓
Standard
  分析用の列名へ変換
  型・表記を統一
  key_商品コード、key_得意先コードなどを作成
  ↓
Merge
  同じ変換規則を適用したキーで結合
  ↓
Analysis
  集計粒度に合うキーだけを残すか、新しく作成
  ↓
Report
  読み手に必要な列を出力
```

## 判断基準

- 結合する両側で表記揺れや型の違いがあり得るなら、両側に`key_`列を作る。
- 原本と分析用の名称を混ぜず、どの層で名前を変えたかを追えるようにする。
- グループ化後は、元のキーが現在の粒度を表せるか確認する。
- `key_`列は内部処理用であり、最終出力へ残す理由がなければ除く。
- キーの名前は、何を結合するための値かが分かる形にする。
