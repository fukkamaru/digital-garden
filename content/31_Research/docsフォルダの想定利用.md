# docsフォルダの役割と構成例

## 概要

docsフォルダは、一般にプロジェクトや製品に関するドキュメントをまとめる場所として使われる。ただし、名称だけで用途が一意に決まるわけではない。コードリポジトリ内のdocsと、組織の共有フォルダとしてのdocsでは、置くべき文書や公開範囲が異なる。

## 想定される文書

### プロジェクト運営

- 要件定義書
- 仕様書
- 設計書
- 計画書
- 意思決定記録
- 会議の議事録やアジェンダ

### 利用者向け

- ユーザーマニュアル
- インストールガイド
- 操作手順書
- FAQ
- トラブルシューティング

### 開発・運用向け

- 開発環境の構築手順
- アーキテクチャ説明
- APIやデータ構造の説明
- デプロイ・運用手順
- 障害対応手順

### 調査・報告

- 調査レポート
- 分析結果
- 参考資料
- 定期報告書

### 再利用する資料

- 文書テンプレート
- フォーム
- チェックリスト
- 記入例

## 構成例

~~~text
docs/
├─ README.md
├─ getting-started/
├─ guides/
├─ reference/
├─ architecture/
├─ operations/
├─ decisions/
└─ assets/
~~~

- README.md：docs全体の案内と入口
- getting-started：導入手順
- guides：目的別の操作・作業ガイド
- reference：仕様や参照情報
- architecture：設計と構造の説明
- operations：運用・保守・障害対応
- decisions：重要な判断とその理由
- assets：文書から参照する画像など

## 用途を決めるときの判断基準

- 誰が読むのか。
- 公開用か、組織内限定か。
- 文書の責任者と更新方法は決まっているか。
- ソースコードと一緒に版管理すべきか。
- 機密情報や個人情報を含むか。
- 他の保存場所と重複しないか。

## 注意点

契約書、NDA、個人情報、認証情報などは、アクセス制御のない公開リポジトリのdocsへ置かない。機密文書を扱う場合は、適切な権限管理と保存期間を設定できる専用の保管場所を使う。

docsを作るだけでは情報は維持されない。入口となるREADME、分類ルール、更新責任、古い文書の扱いをあわせて定めると、後から参照しやすくなる。
