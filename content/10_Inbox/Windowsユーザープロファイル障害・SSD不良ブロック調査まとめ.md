以下に、このチャットの最初から最後までを、**発生事象・確認内容・実施した操作・判明した原因・現在の判断・今後の対応方針**に分けて整理します。

# Windowsユーザープロファイル障害・SSD不良ブロック調査まとめ

## 1. 発生した問題

PC起動時にWindowsから、

- 「アカウントにサインインできません」
- 「今すぐサインアウトしない場合、作成するファイルや変更の内容はすべて失われます」

という警告が表示された。

同時に、

- 元々のデスクトップが消えたように見える
- 以前設定していた共有フォルダ等がなくなっている
- 共有フォルダを設定し直しても、再起動すると再び消える
- ログイン画面ではユーザー名が `user` のみ表示される
- 元のユーザー名・アカウント構成が不明

という症状が発生していた。

当初、この状態から**Windowsが一時プロファイル（Temporary Profile）でログインしている可能性が高い**と判断した。

---

# 2. `C:\Users` の確認

`C:\Users` 以下を確認したところ、

- `C:\Users\user`
- `C:\Users\TEMP`

が存在していた。

さらに `C:\Users\user` 内を確認すると、

- デスクトップ
- ドキュメント
- その他、以前から使用していたと思われるファイル類

が残っていた。

特に、

`C:\Users\user\Desktop`

には、本来あるべきデスクトップファイルが存在していた。

この時点で、

**元のユーザーデータそのものが消えたわけではない**

と判断した。

---

# 3. 現在使用中のプロファイル確認

cmdで、

```
echo %USERPROFILE%
```

を実行。

結果：

```
C:\Users\TEMP
```

となった。

これにより、現在の `user` アカウントが本来の

```
C:\Users\user
```

ではなく、

```
C:\Users\TEMP
```

を使用していることが確定した。

つまり、

```
userアカウント
    ↓
本来：C:\Users\user
    ↓
読み込み失敗
    ↓
現在：C:\Users\TEMP
```

という状態だった。

---

# 4. ProfileList レジストリ確認

次の読み取り専用コマンドを使用した。

```
reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList" /s /v ProfileImagePath
```

その結果、次の構造が確認された。

```
S-1-5-21-2339841069-1987575619-3461696281-1001
    ProfileImagePath = C:\Users\TEMP

S-1-5-21-2339841069-1987575619-3461696281-1001.bak
    ProfileImagePath = C:\Users\user
```

つまりWindowsは、

- 通常のSID `-1001` → TEMP
- `.bak` 側 → 本来の `C:\Users\user`

という状態にしていた。

典型的な**ユーザープロファイル読み込み失敗後の `.bak` 状態**だった。

---

# 5. `State` と `RefCount` の確認

通常側：

```
ProfileImagePath = C:\Users\TEMP
FullProfile      = 0x1
State            = 0x4a04
```

`.bak` 側：

```
ProfileImagePath = C:\Users\user
FullProfile      = 0x1
State            = 0x8000
```

だった。

一方で、

```
RefCount
```

はどちらにも存在していなかった。

この点については、

**RefCountは必ず存在する値ではないため、存在しないこと自体を異常とは判断しない**

とした。

また、存在しない `RefCount` を不用意に新規作成する方針も採らなかった。

---

# 6. レジストリバックアップ

ProfileListを修復する前にバックアップを作成しようとした。

最初、

```
reg export "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList" "C:\Users\Public\Documents\ProfileList_backup_20260820.reg"
```

を通常cmdで実行したが、

```
ファイルに書き込めません
```

というエラーになった。

管理者cmdでも同じ保存先では失敗した。

そのため保存先を、

```
C:\
```

直下へ変更。

```
reg export "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList" "C:\ProfileList_backup_20260820.reg"
```

を実行したところ成功した。

後にシステムの復元なども行ったため、改めて、

```
C:\ProfileList_backup_20260820_1337.reg
```

も作成した。

さらに、このレジストリバックアップもSMB経由で別端末へ退避した。

---

# 7. 元ユーザーフォルダのバックアップ

修復作業前に、

```
C:\Users\user
```

を、コピー可能な範囲でSMB経由で別端末へ丸ごと退避した。

方針としては、

- Desktop
- Documents
- Pictures
- Downloads
- その他の業務ファイル
- コピー可能なAppData内データ

などを退避。

ただし、

- 使用中
- アクセス拒否
- システム保護
- ジャンクション

等でコピーできないものについては、無理に権限変更してまでコピーしないこととした。

また、このSMBコピーは、

**ユーザーデータのバックアップであって、完全なWindowsユーザープロファイルバックアップではない**

という整理をした。

---

# 8. システムの復元を検討

手動でProfileListを書き換える前に、Windows標準の「システムの復元」と比較した。

唯一存在していた復元ポイントは、

```
2026/08/19 07:30:38
Windows Update
```

だった。

「影響を受けるプログラムの検出」では、

Microsoft Edgeのバージョン変更程度しか表示されなかった。

当初は、

- 問題発生前に近い復元ポイント
- 変更範囲が比較的小さい
- レジストリ等をWindows標準機能で戻せる

という理由から、ProfileList手動修復より先にシステムの復元を試すことにした。

---

# 9. システムの復元結果

2026/08/19 07:30:38の復元ポイントへ復元した。

しかし、

**問題は改善しなかった。**

引き続き `user` でログインすると一時プロファイルになった。

この時点では、

「復元ポイント時点より前に問題があった可能性」

も考えたが、後のイベントログ調査によって、この推測は修正されることになった。

---

# 10. 修復用ローカル管理者の作成

TEMPプロファイル上で直接 `user` 自身を修復するより、

**別の独立した管理者アカウントから修復する方が安全**

と判断した。

修復用アカウント名として、

```
repairadmin
```

を採用。

パスワード付きローカルアカウントとして作成し、管理者権限を付与。

初回ログイン後、

```
echo %USERPROFILE%
```

を実行すると、

```
C:\Users\repairadmin
```

となった。

つまり `repairadmin` は正常な独立プロファイルとして作成された。

---

# 11. repairadminからProfileListを再確認

システムの復元後かつ `repairadmin` 作成後のProfileListを再確認した。

その時点では、

```
...-1001.bak → C:\Users\user
...-1002     → C:\Users\repairadmin
```

だけが存在しており、

```
...-1001
```

の通常キーは存在していなかった。

これは、`user` にログインしていない間はTEMP側のキーが存在しないためだった。

`user` にログインすると、再び、

```
...-1001      → C:\Users\TEMP
...-1001.bak  → C:\Users\user
```

が作られることも確認された。

---

# 12. ProfileListの手動修復

元ユーザーにログインしていない状態で、

```
...-1001.bak
```

だけが存在していたため、修復を実施した。

実施内容：

### 変更1

```
S-1-5-21-...-1001.bak
```

から `.bak` を外し、

```
S-1-5-21-...-1001
```

へ変更。

### 変更2

そのキー内の

```
State = 0x8000
```

を、

```
State = 0
```

へ変更。

最終的には、

```
...-1001
    ProfileImagePath = C:\Users\user
    State            = 0

...-1002
    ProfileImagePath = C:\Users\repairadmin
```

となった。

`RefCount` は存在しなかったため、新規作成も変更もしなかった。

---

# 13. ProfileList修復後の結果

Windowsを再起動し、`user` へログイン。

しかし、

**再び「アカウントにサインインできません」が表示された。**

`repairadmin` に戻りProfileListを確認すると、

再び、

```
...-1001      → C:\Users\TEMP
...-1001.bak  → C:\Users\user
...-1002      → C:\Users\repairadmin
```

へ戻っていた。

このことから、

**ProfileListのレジストリ不整合は根本原因ではない**

と判断した。

Windowsは `C:\Users\user` を読み込もうとして失敗し、その結果として `.bak` とTEMPを再生成していた。

---

# 14. イベントビューアー調査

次に、

```
Windowsログ
→ Application
→ User Profile Service
```

を確認。

イベントIDとして、

- 1502
- 1508
- 1509
- 1511
- 1515

等が存在していた。

まず1508を確認。

直近の1508では、

```
(null)\ntuser.dat
指定されたパスが見つかりません
```

という内容が表示された。

これにより、

ユーザープロファイルのレジストリハイブである、

```
C:\Users\user\NTUSER.DAT
```

周辺に問題がある可能性が高まった。

---

# 15. NTUSER.DATの確認

repairadminから、

```
dir /a "C:\Users\user\NTUSER.DAT"
```

を実行。

結果：

```
ファイルが見つかりません
```

だった。

さらに、

```
dir /a "C:\Users\user\NTUSER*"
```

を実行。

結果として、

- `ntuser.dat.log1`
- `ntuser.dat.log2`
- `NTUSER.DAT{GUID}.TM.blf`
- `NTUSER.DAT{GUID}.TMContainer....regtrans-ms`
- `ntuser.ini`

などは存在したが、

**`NTUSER.DAT` 本体だけが存在しなかった。**

この時点で、

```
C:\Users\user
 ├ Desktop             → 残っている
 ├ Documents           → 残っている
 ├ AppData等           → 残っている
 └ NTUSER.DAT           → 欠落
```

という状態だと分かった。

---

# 16. シャドウコピー確認

`NTUSER.DAT` の過去コピーが残っていないか確認するため、

```
vssadmin list shadows
```

を実行。

シャドウコピーは、

```
2026/08/20 08:55:40
2026/08/20 10:09:56
2026/08/20 12:36:52
2026/08/20 13:46:03
```

の4つだけだった。

しかし後に時系列を再確認した結果、

**問題は8月19日時点ですでに発生していた**

ため、8月20日のシャドウコピーは正常な `NTUSER.DAT` の救出元としては価値が低いと判断した。

---

# 17. 8月18日・19日のイベントログを再確認

ユーザーから、

- 8月18日の業務時間中は正常に使用できていた
- 8月18日のUser Profile Serviceログも正常読み込みだった
- 8月19日にはすでに問題が発生していた

という情報が得られた。

そこで8月19日の最初期のイベント1508を確認した。

結果：

```
C:\Users\user\ntuser.dat
データ エラー
（巡回冗長検査（CRC）エラー）
```

だった。

これは非常に重要な情報だった。

つまり8月19日時点では、

**NTUSER.DAT自体は存在していたが、ストレージから正常に読み込めなかった**

ことが分かった。

---

# 18. 正しい時系列

ここまでの情報から、時系列は次のように整理された。

```
2026/08/18
    userプロファイル正常
    User Profile Serviceも正常
    NTUSER.DATも正常に読み込み

        ↓

2026/08/19 07:30:38
    Windows Update
    復元ポイント作成

        ↓

2026/08/19 17:17頃
    C:\Users\user\NTUSER.DAT の読み込みでCRCエラー

        ↓

    userプロファイル読み込み失敗

        ↓

    ProfileListの元SIDが.bak化

        ↓

    TEMPプロファイル作成

        ↓

2026/08/20
    障害対応開始

        ↓

    ProfileList修復を試す
    → NTUSER.DATを正常に読めないため再び失敗

        ↓

    TEMP / .bakが再生成
```

したがって、

**Windows Updateの復元ポイントより前から壊れていたとは限らず、8月19日7:30～17:17の間にストレージ読み取り障害が発生した可能性が高い**

と修正した。

---

# 19. DiskイベントID 7の発見

さらに、

```
Windowsログ
→ システム
```

を確認。

すると、8月19日17:17頃に大量の、

```
ソース：disk
イベントID：7
```

が存在していた。

内容：

```
デバイス \Device\Harddisk0\DR0 に不良ブロックがあります。
```

だった。

しかも、

- 7件程度ではない
- 100件以上発生
- 8月19日だけでなく8月20日も継続

していることが分かった。

---

# 20. 根本原因の判断

この時系列が極めて重要だった。

```
8/19 17:17:27頃
Disk イベントID 7
Harddisk0 に不良ブロック

        ↓

ほぼ同時刻

User Profile Service 1508
C:\Users\user\NTUSER.DAT
CRCエラー

        ↓

userプロファイル読み込み不能

        ↓

TEMPプロファイル
```

このため、今回の根本原因については、

**Windows UpdateやProfileListの単純なレジストリ障害ではなく、ストレージ側の読み取り障害が最も有力**

と判断した。

ProfileListの `.bak` は原因ではなく、

**ストレージ障害によるプロファイル読み込み失敗の結果**

と考えるのが最も整合的。

---

# 21. 新規ユーザー作成方針の変更

当初は、

```
新しい本番ユーザーを作成
↓
旧userからデータ移行
```

を考えていた。

しかし、

**同じHarddisk0上でイベントID 7が100件以上継続**

していることが判明したため、

このディスク上で新しい本番ユーザーを作り、環境構築するのは止めることにした。

理由：

新しいユーザーを作っても、

```
C:\Users\新ユーザー
```

は同じ物理ストレージ上に作られるため、再びファイル破損する可能性がある。

`repairadmin` は緊急用・調査用として残すが、本番利用はしない。

---

# 22. SSDでも不良ブロックは起きるか

PCがSSD搭載機である可能性が高いため、

「HDDなら理解できるが、SSDでもこのようなことが起きるのか」

という確認を行った。

結論：

**SSDでも起きる。**

HDDの不良セクタとは内部の仕組みは異なるが、Windowsから見れば、

```
その論理ブロックを正常に読み書きできない
```

という結果は同じため、

```
イベントID 7
不良ブロック
```

として記録されることがある。

SSDでは、

- NANDフラッシュの劣化
- SSDコントローラ異常
- ファームウェア異常
- 予備ブロックへの再配置失敗
- 接続系統の異常
- 電源系統
- SATA SSDならケーブル・端子
- NVMeならSSD本体・PCIe接続

等が候補になる。

ただし、この段階では、

**SSD本体が故障確定とまでは断定しない**

という整理をした。

---

# 23. PC機種：Panasonic CF-LV

PCは、

```
Panasonic Let's note CF-LVシリーズ
```

であることが判明。

CF-LVシリーズではSSDを搭載するモデルがあり、ストレージ交換自体は可能な構造のモデルがある。

ただし、

- ユーザーがワンタッチで交換するベイではない
- 底面カバーを外して内部SSDへアクセスする必要がある
- 正確なSSD規格・M.2サイズ等は完全なCF-LV型番を確認してから判断

という整理になった。

また今回のようにストレージエラーが出ている場合、

**旧SSDをそのままクローンして使うより、新SSDへWindowsをクリーンインストールする方を推奨**

とした。

理由は、

破損したファイルシステム・ユーザープロファイル・不良データを新SSDへそのまま持ち込むリスクがあるため。

---

# 24. 使用環境：粉塵の多い充填室

このPCは、

**粉塵が舞う充填室**

で使用されていることが判明した。

「HDDなら粉塵の影響は理解できるが、SSDでも原因になり得るか」

という確認を行った。

結論：

**SSDでも粉塵環境は無関係ではない。**

ただし、

「粉塵がNANDフラッシュを直接傷つけて不良ブロックになる」

という単純な構図ではない。

考えられる経路は、

### 冷却不良

粉塵が、

- 冷却ファン
- ヒートシンク
- 吸排気口

へ蓄積。

その結果、

- SSDコントローラ
- CPU
- チップセット
- 基板

の温度が上昇し、長期的な劣化を促進する可能性がある。

### 接触不良

粉塵が、

- M.2 SSD端子
- 基板
- コネクタ

周辺に堆積し、接触不良につながる可能性。

### 吸湿

粉塵の種類によっては吸湿し、

- 漏電
- 絶縁低下
- 腐食
- 接点不良

を起こす可能性。

### 導電性粉塵

特に、

- 金属粉
- カーボン
- 一部顔料

等の導電性粉塵では、

基板上で短絡・リーク等の電気的異常を起こす可能性がある。

### 化学的影響

油分・薬品・腐食性物質を含む粉塵なら、

基板・コネクタの腐食や汚染につながる可能性がある。

---

# 25. 粉塵が今回の直接原因か

現時点では、

**粉塵が今回のSSD障害の直接原因だったとは証明できない。**

一方で、

- 粉塵が舞う充填室
- PC内部への粉塵侵入可能性
- DiskイベントID 7が100件以上
- NTUSER.DATでCRCエラー
- 実際のデータ破損

という状況から、

**粉塵環境を無関係として扱うべきではない**

と判断した。

今後SSDを交換する場合も、

**SSDだけ交換して内部清掃をしないのは不十分**

であり、

- ファン
- ヒートシンク
- SSD周辺
- 基板
- 吸排気口

の粉塵堆積状態も確認するべきとした。

---

# 26. 現時点での最終判断

今回の障害は、当初考えていた、

```
Windowsユーザープロファイルのレジストリ障害
```

だけではない。

現時点では、

```
ストレージの読み取り障害
    ↓
NTUSER.DATでCRCエラー
    ↓
userプロファイル読み込み失敗
    ↓
ProfileListが.bak化
    ↓
TEMPプロファイルへフォールバック
```

という流れが最も整合的。

したがって、

**ProfileListの `.bak` は根本原因ではなく二次症状**

と考える。

---

# 27. 今後やらない方がよいこと

現時点では以下を避ける。

- 元の `user` プロファイルを何度も修復しようとする
- `.bak` / `State` の変更を繰り返す
- 同じSSD上に新しい本番ユーザーを構築する
- `NTUSER.DAT.LOG1/LOG2` を `NTUSER.DAT` に単純改名する
- 古い `C:\Users\user` を削除する
- `TEMP` を削除する
- `repairadmin` を削除する
- バックアップ済みProfileListを削除する
- データバックアップ完了前に `chkdsk /r` を実行する

特に `chkdsk /r` はディスク全面を読み取るため、

**劣化中のストレージに大きな負荷を与える可能性がある**

ので、データ保全より先に実施しない。

---

# 30. 今回の重要な結論

今回の調査で最も重要だったのは、単に、

```
user → TEMP
```

となっていることではない。

そのさらに前段階で、

```
Disk Event ID 7
Harddisk0 に不良ブロック

＋

User Profile Service 1508
C:\Users\user\NTUSER.DAT
CRCエラー
```

が**同時刻に発生していたこと**。

このため今回の事象は、

**「ユーザープロファイルが突然壊れた」のではなく、「ストレージ読み取り障害によってユーザープロファイルの重要ファイル `NTUSER.DAT` が読めなくなり、その結果としてTEMPプロファイルへ移行した」**

と整理するのが最も妥当。

さらにDiskイベントID 7が100件以上、翌日まで継続しているため、

**現在のストレージを今後も本番利用すること自体にリスクがある**

というところまで判断が進んだ。
