# AI管理領域とZettelkasten領域のフォルダ境界を明示する

AIにローカルのフォルダ構成について相談するとき、**AI向けのルールやコンテキストを保存している側**と、**Zettelkastenとして知識や作業ファイルを管理している側**を、AIが同一のフォルダツリーとして解釈してしまう問題がある。

単に「用途が違う」と説明するだけでは不十分であり、両者を**別のルートを持つ独立したフォルダツリーとして扱わせる必要がある**。

---

## 問題が発生した背景

ローカル環境には、大きく分けて役割の異なる二つの領域がある。

|呼称|主な役割|
|---|---|
|**AI側**|AI向けルール、コンテキスト、Work Skills、作業方法などの管理|
|**ZK側**|Zettelkasten、Research、Inbox、知識ノート、ZK関連作業の管理|

しかしAIとの会話では、

- コンテキスト側
- 作業フォルダ
- Zettelkasten用フォルダ
- 03
- 04_Context
- 同じ階層
- そちら側

などの表現を使用する。

これらは人間には文脈から区別できても、AIはそれぞれを一つのフォルダ構造上の要素として結びつけてしまうことがある。

実際に、Zettelkasten側について、

> 03でログ管理などをするフォルダを作ったらよいか

という話をしていた際、AIがAI側の`04_Context`まで同じ階層の構成要素として持ち込み、両者を混ぜた状態でフォルダ設計を考え始めた。

問題は名称そのものではなく、**AIが別々のルートを頭の中で一つの仮想ツリーへ統合してしまったこと**にある。

---

## 本来の構造

概念的には次のように考える。

```
[AI側]
└─ AI向けルール・コンテキスト
   └─ 04_Context
   └─ その他AI運用用ファイル

[ZK側]
└─ Zettelkasten
   ├─ 01_Templates
   ├─ 02_images
   ├─ 10_Analytics
   ├─ 20_Journal
   ├─ 21_Reading
   ├─ 30_Inbox
   ├─ 31_Research
   └─ 32_Zk
```

重要なのは、上の二つが**独立したルート**であること。

したがって、AIは以下のような仮想構造を作ってはならない。

```
03_???
04_Context
10_Analytics
20_Journal
30_Inbox
31_Research
32_Zk
```

`03`や`04`という番号が近いからといって、同じ親フォルダの下にあるとは限らない。

---

## 「役割の説明」だけでは不足する

当初は、

- AI管理領域
- Zettelkasten領域

という正式名称を決め、それぞれの用途を説明すれば混同を防げると考えた。

しかし実際の誤解釈を見ると、それだけでは弱い。

AIは、

> AI側とZK側は用途が違う

と理解していても、フォルダ配置を考える段階では、

> 03の次なら04_Contextがある

といった形で再び両者を同一階層へ統合する可能性がある。

そのため必要なのは、

> 用途が異なる

というルールではなく、

> **異なるROOT間のフォルダを親・子・兄弟として関連付けてはいけない**

という構造上の制約である。

---

## 必要な境界ルール

AIがフォルダ構成を解釈するときは、まずどちらのルートについて話しているのかを確定する。

```
AI_ROOT
ZK_ROOT
```

その後の推論は、そのROOT内部に限定する。

### AI側について話している場合

AI向けルール、コンテキスト、Work Skillsなどについて考える。

ZK側の、

- Inbox
- Research
- Zk
- ZK用システムフォルダ

などを同一階層の候補として持ち込まない。

### ZK側について話している場合

Zettelkasten内部のフォルダ構成だけを対象にする。

AI側の、

- `04_Context`
- AIルール
- Work Skills

などを比較対象、兄弟フォルダ、親フォルダとして持ち込まない。

---

## 特に禁止したい推論

AIには次の推論を明示的に禁止する必要がある。

1. **番号から階層関係を推測する**
    - `03`と`04_Context`が存在するから同一階層と判断する。
    - `01`、`02`、`03`、`04`という番号の連続性から構造を補完する。
2. **別ROOTのフォルダを配置判断へ持ち込む**
    - ZK側で`03`を検討しているときに、AI側の`04_Context`との並びを考える。
3. **用途の似たフォルダを自動的に関連付ける**
    - 「ログ」「コンテキスト」「システム」という意味が近いからといって、別ROOT間で関係付ける。
4. **相対表現をROOTをまたいで解釈する**
    - 「同じ階層」
    - 「そちら」
    - 「この上」
    - 「03」
    などは、現在話しているROOTの内部だけで解釈する。

---

## `04_Context`の位置付け

`04_Context`は、AI側のコンテキスト保存場所である。

Zettelkasten内部のStructureノートやResearch、作業用システムフォルダなどとは別物。

したがって、

> ZK側に03のシステムフォルダを作る

という話をしている際に、

> 04_Contextの隣に03を置く

などと解釈してはいけない。

`04_Context`という名称や番号は、**AI側というROOT内部でのみ意味を持つ**。

---

## スマホからの入力負担

毎回、

```
ZETTELKASTEN_ROOT
AI_CONTEXT_ROOT
```

のような長い名称をスマホから入力する運用は現実的ではない。

そのため、会話上では短い正式名称を使用する。

|短縮名|意味|
|---|---|
|**AI側**|AI向けルール・コンテキスト等のフォルダツリー|
|**ZK側**|Zettelkastenを管理するフォルダツリー|

これなら、

> ZK側の03について

> AI側のContextについて

程度の入力で済む。

毎スレッドで長い構造説明を入力するのではなく、**境界ルールそのものをAI側の開始コンテキストへ保存し、ユーザーは短縮名だけを使う**方がよい。

---

## 基本ルール案

AI側の開始コンテキストには、少なくとも次の趣旨を記載する。

> この環境には「AI側」と「ZK側」という独立した二つのフォルダツリーが存在する。
> 
> 両者は別ROOTであり、一つのフォルダツリーとして統合して解釈してはならない。
> 
> 片方に存在するフォルダを、もう片方のフォルダの親・子・兄弟として扱ってはならない。
> 
> `01`、`02`、`03`、`04`などの番号は、それぞれのROOT内部でのみ意味を持つ。番号の連続性から別ROOTとの関係を推測してはならない。
> 
> ZK側について話している場合、AI側の`04_Context`などを配置判断へ持ち込まない。
> 
> AI側について話している場合、ZK側のInbox、Research、Zkなどを同一階層として扱わない。
> 
> 「03」「同じ階層」「そちら」などの相対表現は、現在話しているROOT内部だけで解釈する。
> 
> 別ROOTへ話題を移すのは、ユーザーが明示した場合のみとする。

---

## Workspace Boundaryという考え方

より強く誤解釈を防ぐなら、全体ルールとは別に「現在どちらについて作業しているか」を示す境界を持たせる方法もある。

たとえばZK整理中なら、

```
Current workspace: ZK側
```

という状態を持たせ、

```
flowchart LR
    A[現在の作業対象] --> B[ZK側]
    B --> C[03などのシステム領域]
    B --> D[10_Analytics]
    B --> E[30_Inbox]
    B --> F[31_Research]
    B --> G[32_Zk]

    H[AI側] --> I[04_Context]
```

という認識に固定する。

ただし、これをユーザーがスマホから毎回入力するのは負担が大きい。

理想は、AIが開始時に読むコンテキストや作業ルールから自動的に現在の領域を把握し、ユーザー側は必要な場合だけ、

> ZK側

> AI側

と指定すれば済む運用である。

---

## 方針

今回の問題への対策は、単純な名称変更ではなく次の三段階で考える。

1. **AI側とZK側を独立したROOTとして定義する**
2. **ROOTをまたいだ階層推論を禁止する**
3. **会話では「AI側」「ZK側」という短い識別子だけを使う**

特に重要なのは2である。

「AI側とZK側は違う」と説明するだけではなく、

> **別ROOTに存在するフォルダを材料として、現在のROOTの構造を補完・推測してはいけない**

ところまで明文化する必要がある。

---

## 決定事項

- AI向けルール・コンテキストを管理している側とZettelkasten側を、独立したフォルダROOTとして扱う。
- 会話上の短縮名は**「AI側」「ZK側」**を基本とする。
- `04_Context`はAI側に属し、ZK側のフォルダ構成判断には使用しない。
- ZK側で検討する`03`などの番号と、AI側の`04_Context`の番号を関連付けない。
- ROOT間の親子・兄弟関係をAIが推測することを禁止する。
- スマホから長いROOT名や構造説明を毎回入力する運用にはしない。
- 長い境界ルールはAI向けコンテキストに保存し、日常会話では短い識別だけで済ませる。

## Outstanding issues

- 境界ルールを`_AI Start Here.md`へ直接入れるか、別のルールファイルとして分離するか。
- ZK側専用の作業開始コンテキストにもWorkspace Boundaryを持たせるか。
- ZK側で検討している`03`フォルダの正式な名称・役割については別途決定する。

## Next actions

AI向けコンテキストを次に修正する際は、単なる「AI側／ZK側の説明」ではなく、**ROOT分離とROOT越境推論禁止を明示したルール**として追加する。
