ビジネスシーンにおいて、一般に **Product Requirements Document（プロダクト要求仕様書／製品要求仕様書）** のことを指す。

簡単に整理すると
- 何を作るのか：What
- 誰のために作るのか：Whom / Who
- なぜ作るのか：Why
- 何を満たせば完成か：Success Criteria / Acceptance Criteria

を整理した文章である。

## PRDの役割

PRDは、企画・デザイン・開発・営業などの関係者間で、プロダクトについての認識を揃えるために使う。

```text
顧客・業務上の問題
↓
解決したいこと
↓
必要な機能・要件
↓
成功条件
↓
設計・開発
```

特に重要なのは、単なる「機能一覧」ではなく、**なぜその機能が必要なのかまで定義すること**にある。

## PRDに記載する代表的な項目

| 項目     | 内容                       |
| ------ | ------------------------ |
| 背景・課題  | 何が問題なのか                  |
| 目的     | PRDによって何を実現するのか          |
| 対象ユーザー | 誰が使うのか                   |
| ユースケース | どのような場面で使うのか             |
| 要求事項   | 必要な機能・振る舞い               |
| 非機能要件  | 性能、セキュリティ、対応環境など         |
| スコープ   | 今回やること／やらないこと            |
| 優先順位   | Must / Should / Could など |
| 成功基準   | 何をもって成功と判断するか            |
| 制約     | 予算、期限、技術、法規など            |
| 未解決事項  | まだ判断できていない点              |

### 例

たとえば、「営業担当者向けの在庫確認システム」を作る場合、PRDは次のようになります。

```text
目的：
営業担当者が外出先から最新在庫を確認できるようにする。

課題：
現在は営業担当者が事務所へ電話して在庫を確認している。

対象ユーザー：
営業担当者

必須要件：
- 商品コード・商品名から検索できる
- 現在庫数を表示する
- スマートフォンから利用できる

今回の対象外：
- 発注機能
- 在庫修正機能

成功基準：
在庫確認のための社内電話を80%削減する。
```

## PRDと「設計書」の違い

ここは混同されやすい部分です。

| 文書         | 主に答える質問      |
| ---------- | ------------ |
| PRD        | **何を・なぜ作るか** |
| UI/デザイン仕様書 | **どう見せるか**   |
| 技術設計書      | **どう実装するか**  |
| テスト仕様書     | **どう確認するか**  |

したがって、基本的には、

```text
PRD
↓
デザイン・技術設計
↓
実装
↓
テスト
```

という順序になる。

PRDは社内ツール、Webサービス、EC機能、業務システム、動画コンテンツなど、**「何かを新しく作る・改善する案件」全般で使える要求整理の形式**と考えると分かりやすい。
