# PHPの脆弱性とWordPressのセキュリティ

2026年10月21日、PHPに存在する2件の重大な脆弱性を修正したセキュリティアップデートが公開された。

今回の問題は、WordPress自体の欠陥ではなく、それを動かすPHPの実行環境に存在する欠陥である。

**Webサイトの安全性は、サイトに実装された機能だけではなく、そのサイトを動かすソフトウェアやサーバー環境にも依存する。**

## WordPressはPHPを利用して動作する

Webサイトを構成する技術は、役割によって区別できる。

| 要素 | 主な役割 |
| --- | --- |
| WordPress | 記事やWebサイトの内容を管理するCMS |
| PHP | WordPressのプログラムを実行する |
| Webサーバー | ブラウザからのアクセスを受け付ける |
| データベース | 記事、設定、ユーザー情報などを保存する |

WordPressのプログラムはサーバー上に配置され、PHPの実行環境を利用して動作する。

そのため、WordPressを更新することと、PHPを更新することは別の操作になる。

今回の脆弱性はPHP側の問題なので、WordPress本体やプラグインだけを更新しても解消しない。

## 2026年10月に発覚した脆弱性

今回の脆弱性は、次の2件である。

- `CVE-2026-109618`：メモリ不足時の内部処理に関する欠陥
- `CVE-2026-109619`：解放済みメモリに関連する内部状態の取り扱いに関する欠陥

いずれもCVSS v4.0で深刻度9.2と評価された。

条件が成立すると、認証されていない第三者がサーバー上で不正なプログラムを実行できる可能性がある。

これはリモートコード実行（Remote Code Execution：RCE）と呼ばれる。

### サイトの機能が少なくても攻撃対象になる

例えば、次のような機能しか持たないWebサイトであっても、PHPの脆弱性の影響を受ける可能性がある。

- 製品やサービスの紹介
- お知らせの掲載
- 記事の公開
- 企業情報の閲覧

決済機能や会員登録機能がないことは、扱う個人情報の少なさなどの点では有利である。

しかし、PHP自体に脆弱性が存在する場合、サイトの機能が単純であることだけでは安全を保証できない。

想定される被害には、サイトの改ざん、不正ページの設置、悪意あるサイトへの誘導、サーバーの不正利用などがある。

ただし、脆弱性の存在と実際の侵害は区別する必要がある。

## PHPの更新はサーバー側の管理である

WordPressの管理画面にログインできることと、PHPを更新する権限を持つことは別である。

### WordPressの管理

- 記事の作成・編集
- 画像の登録
- ページの管理
- WordPressの設定
- 権限に応じたテーマ・プラグインの管理

### サーバーの管理

- PHPのバージョン変更
- PHPの設定変更
- データベースの管理
- サーバーの保守
- 実行環境へのセキュリティ修正の適用

一般的に、WordPress管理画面とレンタルサーバーの管理画面は別々に用意されている。

ただし、PHPの更新方法はサーバーの運用形態によって異なる。

| 運用形態 | PHP更新の担当 |
| --- | --- |
| レンタルサーバー | 事業者が更新を提供し、自動適用または利用者による切り替え |
| 外部保守委託 | 保守担当者・制作会社など |
| 自社管理サーバー | 自社のシステム管理者 |

重要なのは、**WordPressの編集担当者とサーバーの保守担当者を混同しないこと**である。

## PHPの脆弱性への対応

2026年10月21日に公開された修正版は次のとおり。

| PHP系列 | 修正版 |
| --- | --- |
| 8.5 | 8.5.12 |
| 8.4 | 8.4.27 |
| 8.3 | 8.3.36 |
| 8.2 | 8.2.35 |
| 8.1以前 | 公式サポート終了。移行または提供元の個別修正を確認 |

サーバー事業者などが独自に修正を適用する場合もあるため、バージョン番号だけで対策状況を確定できない場合がある。

### WordPressからPHPバージョンを確認する

WordPress管理画面で、

`ツール → サイトヘルス → 情報 → サーバー`

の順に進む。

ここでPHPのバージョンを確認できる。

ただし、この操作でPHPそのものを更新できるわけではない。

### 更新時の注意点

PHPを更新すると、古いWordPressテーマやプラグインとの互換性問題が発生する可能性がある。

そのため、更新前後には次の確認が必要となる。

1. バックアップの有無
2. WordPress・テーマ・プラグインの互換性
3. 公開ページの表示
4. 管理画面の動作
5. 問い合わせフォームなどの主要機能

セキュリティ修正を速やかに適用することと、更新後の動作を確認することは、両方とも必要である。

## Webサイトにアクセスできない場合

今回のような重大な脆弱性が発見されると、サーバー管理者が予防的にWebサイトを一時停止する場合がある。

しかし、アクセスできないことだけを理由に、セキュリティ対策が実施されているとは断定できない。

例えば、Chromeの `ERR_CONNECTION_RESET` は、Webサイトとの接続が途中で切断されたことを示す一般的なエラーである。

原因としては次のようなものが考えられる。

- サーバーの緊急メンテナンス
- セキュリティ対策によるアクセス制限
- サーバー障害
- ネットワーク障害
- プロキシやファイアウォールによる接続遮断

原因の切り分けには、別のブラウザやネットワーク環境からのアクセス確認、公式の障害・メンテナンス情報の確認などが役立つ。

エラー表示だけでサーバー事業者や障害原因を特定することはできない。

## セキュリティ運用における教訓

今回の問題から、次のことが整理できる。

1. **アプリケーションと実行環境は別々の管理対象である。** WordPressを更新してもPHPの脆弱性が修正されるとは限らない。

2. **機能が単純なサイトでも、基盤ソフトウェアの脆弱性に影響される。** 決済機能や会員登録機能がないことは、サーバーの安全性を保証しない。

3. **管理画面へのアクセス権限と保守責任は一致しない。** コンテンツの編集担当者が、サーバーの更新担当者とは限らない。

4. **障害と防御措置は外見だけでは区別できない。** サイトの停止が安全確保のためなのか、単なる障害なのかは、管理者側の情報を確認する必要がある。

5. **修正の適用と動作確認は別の工程である。** セキュリティ上の欠陥を修正したうえで、既存機能が正常に動くことも確認する。

今回の事例は、Webサイトの安全性をWordPress単体の問題として捉えるのではなく、PHP・サーバー・保守体制を含めた仕組みとして理解する必要があることを示している。
