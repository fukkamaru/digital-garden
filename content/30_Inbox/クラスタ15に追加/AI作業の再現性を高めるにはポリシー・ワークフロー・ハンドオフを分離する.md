# AI作業の再現性を高めるにはポリシー・ワークフロー・ハンドオフを分離する

AIにポリシーを読ませていても、スレッドを分けると作業内容や進め方にブレが生じる。

これは単純に「AIがポリシーを無視している」ためではない。ポリシーによって与えられる恒久的なルールと、会話の中で形成される作業状態・局所的な判断・解釈が別物だからである。

## ポリシーだけではスレッド間の状態は再現されない

長いスレッドでは、明示的なポリシー以外にも次のような情報が蓄積されている。

- 今回の作業目的
- 現在どこまで進んでいるか
- 既に決定したこと
- 却下した案
- 今回だけ適用している例外
- ポリシーを今回どのように解釈したか
- 次に実行する作業

会話そのものが一種の作業記憶になっている。

新しいスレッドでは、この作業記憶が失われるため、同じポリシーを読んでもAIが再び解釈を行うことになる。その再解釈の余地が、スレッド間の挙動の差になる。

```
flowchart TD
    A[Policy] --> B[ユーザー指示]
    B --> C[AIの判断]
    C --> D[ユーザーによる修正]
    D --> E[局所的な解釈・例外]
    E --> F[現在の作業状態]

    G[新しいスレッド] --> H[Policy]
    H --> I[局所状態がないため再解釈]
```

AIは決定論的なプログラムではないため、同じ抽象的なルールを読んでも、どの規則を重視するか、どの順序で判断するかには多少の幅がある。

したがって、

> ポリシーを同じものにすれば、すべてのスレッドで完全に同じ挙動になる

とは限らない。

## ポリシーは「方針」ではなく「判断規則」に近づける

スレッド間のブレを減らすためには、ポリシーを抽象的な方針だけで記述するのではなく、AIが実行可能な判断規則に近づける必要がある。

例えば、

> 既存ノートを優先する

だけでは、

- 既存ノートへ追記する
- 既存ノートへリンクする
- 既存ノートを統合先とする
- 新規ノートを作成しない

など複数の解釈が成立する。

より再現性を高めるには、例えば次のように判断順序まで規定する。

```
既存ノートの再利用判断は次の順序で行う。

1. 同一主題の既存Permanentが存在するか確認する。
2. 存在する場合は、新規作成より先に統合可能性を検討する。
3. 統合すると既存ノートの主題が崩れる場合のみ新規ノートを候補とする。
4. 判断できない場合は推測で新規作成せず、確認する。
```

再現性を高めるポリシーでは、少なくとも以下を明示する。

|要素|内容|
|---|---|
|優先順位|複数ルールが競合した場合にどちらを優先するか|
|判断順序|何を先に確認し、次に何を見るか|
|デフォルト動作|判断不能時に作成・停止・確認のどれを選ぶか|
|禁止される推論|AIが不足情報を補完してよい範囲|
|例外条件|原則を外してよい条件|
|停止条件|どこからユーザー確認が必要か|

ポリシーは「思想」だけでなく、可能な部分については実行プロトコルに近づける方がスレッド間の差を抑えやすい。

## Policy・Workflow・Work Stateは別の役割を持つ

一方、すべてをポリシーへ書き込むべきではない。

AIの作業制御情報は、大きく次の3種類に分けられる。

|種類|役割|
|---|---|
|Policy|何をしてよいか、何を正しい状態とするか|
|Workflow / Protocol|どの順序で作業するか|
|Work State / Handoff|現在どこまで進んでいるか|

この3つを混在させると、文書自体が巨大化し、どの情報が恒久的でどの情報が一時的なのか分かりにくくなる。

## 現在のHandoffはZK専用ではない

現在AIルール側に存在するHandoffは、Zettelkasten編集専用のものではない。

様々な業務について、

- 中断した地点
- 現在の状態
- 決定事項
- 次に実行する作業

を記録し、後から再開するための**業務横断型のセーブデータ**として機能している。

そのため、ZK作業のためだけに別のHandoffを新設する必要はない。

また、ZKフォルダ側へHandoffを移す必要もない。

現在の考え方では、Handoffは引き続きAIルール側に置くのが適切である。

## 現在の構成

現状は概ね次のようになっている。

```
AIルール側
├─ AI Start Here
├─ Handoff
└─ Obsidian Zettelkasten AI Operations.md

ZK側
├─ Policy
├─ Roadmap
└─ Zettelkastenノート
```

読み込みの流れは、

```
AI Start Here
↓
Handoff
↓
Obsidian Zettelkasten AI Operations.md
↓
ZK側のPolicy
↓
Roadmap
↓
対象ノート
```

となる。

この構成自体が不適切というわけではない。

AIにとって重要なのは、ファイルが同じフォルダに集まっていることより、**それぞれの責務と読み込み順序が明確であること**である。

## AIにとって問題なのは「散らばり」そのものではない

AIの観点では、ファイルが複数の場所に分かれていることより、次の状態の方が問題になる。

- どのファイルを先に読むべきか分からない
- 同じ規則が複数のファイルに書かれている
- 複数の指示が競合した場合の優先順位がない
- 共通ルールと業務固有ルールが混在している
- Policy・Operations・Workflowの境界が曖昧
- Handoffに恒久ルールまで書かれている

逆に、読み込み経路が一意なら、AIルール側とZK側にファイルが分散していても大きな問題にはならない。

## AI Start Hereはルーターとして機能させる

AIにとって安定した構成にするには、`AI Start Here` 自体へ大量のルールを書くより、何をどの順序で読むかを示す入口として機能させる方がよい。

概念的には次のようになる。

```
AI Start Here
↓
全業務共通ルール
↓
Handoff
↓
今回の業務を特定
↓
対象業務のOperations / Workflow
↓
対象領域のPolicy / Roadmap
↓
必要な対象ファイル
↓
実作業
```

例えばZK作業であれば、

```
AI Start Here
↓
Handoff
↓
Obsidian Zettelkasten AI Operations
↓
ZK Policy
↓
ZK Roadmap
↓
対象ノート
```

となる。

メール整理や広告業務であれば、ZK固有文書を読む必要はない。

このように、Handoffによって「今回どの業務を再開するのか」を特定し、その業務に必要なOperationsやPolicyだけを追加で読む方が効率的である。

## 新しいWorkflowをどこに置くか

新たにWorkflowを追加する場合は、そのWorkflowのスコープによって配置を決める。

### 全業務共通Workflow

例えば、

- 新規スレッド開始時の読み込み順序
- Handoffの読み方
- 作業開始前の確認
- 不足情報がある場合の扱い
- 承認が必要な操作
- 作業終了時のHandoff更新

などであれば、これは全業務共通なのでAIルール側に置く。

概念的には、

```
AI Rules
├─ AI Start Here
├─ AI Work Protocol
├─ Handoff
└─ Domain Operations
```

となる。

### ZK固有Workflow

一方、

- Inbox → Research → Permanentの処理順
- クラスタリング方法
- 統合・分割判断
- Permanent化の手順

などはZK固有である。

この場合、新規Workflowファイルを増やす前に、既存の

`Obsidian Zettelkasten AI Operations.md`

との責務を確認する必要がある。

すでにOperations内に作業手順が多く含まれているなら、別ファイルを新設することでむしろ指示が分散する可能性がある。

## ファイル数を増やすこと自体は目的ではない

AIにとって理想的なのは、

> 1ファイル1責務に近づけつつ、1回の作業で読む必要のあるファイル数は必要最小限にする

ことである。

したがって、新しいWorkflowを追加する前に、既存の

- AI Start Here
- Handoff
- Obsidian Zettelkasten AI Operations
- ZK Policy
- ZK Roadmap

それぞれの責務を確認する必要がある。

特に確認すべきなのは、

> 同じ判断ルールや作業手順が複数ファイルに重複していないか

である。

ファイルが別フォルダにあることよりも、この重複の方がAIの解釈ブレを生みやすい。

## 各文書の責務の暫定整理

現時点では次の役割分担が自然である。

|文書|責務|
|---|---|
|AI Start Here|AIが何をどの順番で読むか|
|共通Workflow / Protocol|AIが業務を開始・再開・終了する共通手順|
|Handoff|現在の業務状態を保存する業務横断セーブデータ|
|Obsidian Zettelkasten AI Operations|AIがZKを扱う際の業務固有ルール・操作手順|
|ZK Policy|Zettelkasten自体の設計原則・判断基準|
|ZK Roadmap|ZKの現在地、改善計画、今後の方向性|

この分離であれば、ZK専用Handoffを追加する必要はない。

## 今回の結論

スレッド間でAIの挙動を安定させるためには、単純にポリシーを増やすのではなく、

```
恒久的な判断規則
        ↓
Policy

作業の進め方
        ↓
Workflow / Operations

現在の作業状態
        ↓
Handoff
```

を分離する必要がある。

また、AIにとってファイルの物理的な配置は二次的であり、最も重要なのは、

1. 各文書の責務が重複していないこと
2. 読み込み順序が一意であること
3. 指示の優先順位が明確であること
4. 必要な文書だけを読む構造になっていること

である。

現在のHandoffは業務横断のセーブデータとして維持し、ZK専用Handoffは追加しない。

新しいWorkflowについては、すぐに新規ファイルを作るのではなく、まず既存の `AI Start Here`、`Obsidian Zettelkasten AI Operations.md`、ZK側Policyとの責務の重複を確認してから、独立ファイル化するか既存文書へ統合するかを判断する。

## 次に検討すること

- `AI Start Here` の責務が読み込みルーターに限定されているか
- `Obsidian Zettelkasten AI Operations.md` にPolicyやWorkflowが混在していないか
- ZK側PolicyにAI固有の作業手順が入り込んでいないか
- 共通Workflowを独立させる必要があるか
- 文書間の優先順位を明文化する必要があるか
- 同一ポリシーを複数スレッドでテストし、判断が分岐する箇所を特定する

次に進めるなら、既存の `AI Start Here`・Handoff・`Obsidian Zettelkasten AI Operations.md`・ZK Policy・Roadmap を実際に比較して、**責務の重複と移動候補だけを洗い出す監査**をするとよいです。
