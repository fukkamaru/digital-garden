# Zettelkastenリファクタリング運用ルールの整理

Zettelkastenの大規模な整理・リファクタリングをChatGPT Workで継続するため、役割の異なる管理ファイルを分離して運用する。

重要なのは、**作業方法を定義するファイル**と、**現在の進捗や作業履歴を保持するファイル**を混同しないことである。

現在の基本構成は次のとおり。

|ファイル|役割|保存先|
|---|---|---|
|`AI Start Here.md`|ZK関連タスクで何を読むかを案内する入口|Context Vault|
|`Obsidian Zettelkasten Ai Operations.md`|ZK全体の操作権限・YAML・リンク・移動・統合・分割・削除などの基本規則|Context Vault|
|`research-zk-refactoring-policy.md`|ZKリファクタリング固有の目的・判断基準・方針|`03_systems/research-zk-refactoring/`|
|`Zettelkasten Refactoring Flow.md`|親クラスタ・子クラスタ・Workスレッド・確認・実行・検証・ログ更新などの進行手順|`03_systems/research-zk-refactoring/`|
|Roadmap|全クラスタの構成、進行順序、完了状態、現在位置、次に処理する範囲を管理|`03_systems/research-zk-refactoring/work/`|
|親クラスタ作業台|各クラスタの対象、子クラスタ構成、依存関係、進捗などを管理|`03_systems/research-zk-refactoring/work/`|
|親クラスタログ|子クラスタごとの作業結果、判断、変更内容、保留事項などを記録|`03_systems/research-zk-refactoring/work/`|

読み込み順序は次のようにする。

```
AI Start Here
↓
Obsidian Zettelkasten Ai Operations
↓
Zettelkasten Refactoring Policy
↓
Zettelkasten Refactoring Flow
↓
Roadmap
↓
現在の親クラスタ作業台
↓
親クラスタログ
↓
対象ノート
```

`Policy` と `Flow` は、今後も再利用する恒久的な運用ルールなので `03_systems` に置く。

一方、Roadmap・作業台・ログは、現在進行中の大規模リファクタリング作業に固有の状態や履歴を保持する。このため、恒久ルールとは分けた `03_systems/research-zk-refactoring/work/` に置く。

したがって、現在の配置は次でよい。

```
content/
├─ 03_systems/
│  └─ research-zk-refactoring/
│     ├─ research-zk-refactoring-policy.md
│     ├─ Zettelkasten Refactoring Flow.md
│     └─ work/
│        ├─ Roadmap
│        ├─ 各親クラスタ作業台
│        └─ 各親クラスタログ
```

Roadmapや作業台・ログは、リファクタリングを終えた後に原則として増えない実行記録として `work/` にまとめる。ログと作業台を別々のサブフォルダへは分けない。

`03_systems/research-zk-refactoring/` は「ZKリファクタリングをどう運用するか」を定義する場所であり、その中の `work/` は「現在の大規模リファクタリング作業を進める作業領域」と考える。

## 子クラスタの処理方法

各親クラスタは、実際に処理できる規模の子クラスタへ分割する。

子クラスタ内部では、ユーザーがAIへ簡単に指示できるよう、各変更提案に単純なIDを付ける。

```
1
2
3
4
...
```

このIDは子クラスタ内だけで使用する一時的な識別子であり、新しい子クラスタでは1から振り直してよい。

変更前には、次の形式で一覧表を提示する。

|ID|ファイル名|ファイルリンク|提案・変更内容|影響範囲|
|---|---|---|---|---|

ユーザーは、

```
1、3はそのまま実行
2は維持
4は提案を変更
```

のようにIDを使って指示できる。

子クラスタの基本サイクルは次のとおり。

```
対象確認・分析
↓
変更提案一覧
↓
ユーザー指示
↓
必要な許可を一括確認
↓
ユーザー承認
↓
次のAI応答で承認済み対象を一括処理
↓
処理結果一覧
↓
ユーザーチェック
├─ 問題あり → 修正 → 再チェック
└─ 問題なし → 次の子クラスタを自動分析
```

許可確認は、可能な限り一つのAI応答にまとめる。

同じ子クラスタについて何度も、

```
確認
↓
回答
↓
再確認
↓
回答
```

と細かく往復しない。

必要な許可をユーザーから受け取った場合は、その直後のAI応答で承認済みの処理をまとめて実行する。

処理後は、再び一覧表を出す。

|ID|ファイル名|ファイルリンク|変更内容|
|---|---|---|---|

ユーザーが問題を指摘した場合は、その対象を修正する。

問題がなければ、その子クラスタを完了とし、同じWorkスレッドで継続可能な場合は、改めて進行許可を求めず次の子クラスタの分析・提案まで進める。

ただし、ユーザーが返答していないことを「問題なし」と解釈してはいけない。

## 文章のリファクタリング・校正

文章をリファクタリング・校正する場合、冒頭だけを書き換える、見出しだけを変える・追加する、一部分だけを整える、といった表面的な変更だけで「完了」としてはならない。

ユーザーが指定した対象範囲全体を最初から最後まで確認し、その範囲全体について必要な整理・校正を行う。

ただし、変更する必要がない部分まで機械的に書き換える必要はない。

重要なのは、**変更量ではなく、対象範囲全体を確認・評価したうえで必要な変更を完了していること**である。

文章を整理するときは、次の内容を損なわない。

- ユーザー自身の意見
- メモ
- 感想
- ニュアンス
- 判断の迷いや留保
- 文脈
- 前後関係
- その記述が生まれた背景
- 他の記述との関係
- 重要な具体例や条件

読みやすくすることを理由に、これらを勝手に削除、一般化、単純化、別の意味へ置き換えない。

元の文章に曖昧さや矛盾がある場合も、AIが勝手に解消した内容へ置き換えず、必要に応じてその状態を維持するかユーザーへ確認する。

構造化では、見出しを増やすこと自体を整理と考えない。

見出しの使用は必要最小限にし、短い文章を多数の見出しへ分割するような過剰な細分化を避ける。

内容に応じて次を使い分ける。

- 文章：説明、理由、文脈、思考の流れ
- 構造化リスト：関連情報や階層的な情報
- 番号リスト：手順、順序、優先順位
- 表：同じ軸で比較できる情報
- Mermaid図：関係、フロー、階層、状態遷移
- 引用符：発言、重要原則、定義
- コードブロック：パス、設定値、構文、構造例

装飾のためには使わず、情報の関係を理解しやすくする場合に使う。

文章のリファクタリング完了前には、少なくとも次を確認する。

1. 対象範囲全体を確認したか
2. 冒頭や見出しだけではなく本文全体を評価したか
3. 重複、冗長性、順序、論理関係を確認したか
4. 元のユーザー情報を不用意に削除していないか
5. 意見、感想、ニュアンス、背景、前後関係を維持しているか
6. AIが新しい主張や意味を勝手に追加していないか
7. 見出し追加だけで整理したことにしていないか
8. 必要に応じて文章、リスト、表、図などを適切に使い分けているか
9. 変更後の文章を最初から最後まで再読し、全体として自然につながっているか

## Workスレッドの扱い

Workスレッドは、親クラスタと一対一にはしない。

原則は、

> 1 Workスレッド = 前の子クラスタで形成された文脈を、後続の子クラスタでも有効に活用できる範囲

とする。

固定の子クラスタ数やノート数では区切らない。

次の要素を見てWorkスレッド境界を判断する。

- 子クラスタ間で共有される文脈
- 依存関係
- 判断の連続性
- 作業の複雑さ
- コンテキスト負荷
- 会話履歴を維持する価値

チャット履歴だけを永続状態として扱わない。

Workスレッドをまたいで必要な情報は、Roadmap、作業台、親クラスタログへ残す。

## 現在の結論

現在の運用構成で、ZKリファクタリング作業は再開してよい。

再開時には、

```
AI Start Here
→ Operations
→ Policy
→ Flow
→ Roadmap
→ 現在の親クラスタ作業台
→ 親クラスタログ
→ 対象ノート
```

の順で必要な情報を確認し、

```
提案一覧
→ ユーザー指示
→ 一括許可
→ 一括実行
→ 結果一覧
→ ユーザー確認
```

のサイクルで各子クラスタを処理する。
