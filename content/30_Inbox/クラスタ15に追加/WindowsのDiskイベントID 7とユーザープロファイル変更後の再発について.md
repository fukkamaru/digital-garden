# WindowsのDiskイベントID 7とユーザープロファイル変更後の再発について

WindowsでSSD/HDDの異常を確認する際、`Disk` をソースとする **イベント ID 7** は、ストレージ上のブロックを正常に読み書きできなかった際に記録されるエラーとして扱われる。

確認場所は次の通り。

> Windowsマークを右クリック → イベント ビューアー → Windows ログ → システム

`Windows ログ → セットアップ` ではない。

イベントビューアーでは「現在のログをフィルター」からイベントID `7` を指定すると確認しやすい。

典型的には、

> デバイス \Device\Harddisk○\DR○ に不良ブロックがあります。

のような内容が記録される。

---

## ID 7は一度発生すると継続するとは限らない

ID 7は「ドライブに問題が存在する限り常に記録され続ける」というものではない。

基本的には、Windowsが問題のある領域に実際にアクセスし、その読み書きで異常が発生した際に記録される。

そのため、同じ問題が存在していても、

- 問題領域を頻繁に読む → 大量に発生する
- たまに読む → 散発的に発生する
- 問題領域を使わなくなる → 発生しなくなる
- SSD/HDD側で問題ブロックが代替処理される → 発生しなくなる

といった違いが生じる。

したがって、

> 以前はID 7が出ていたが、ある時期を境にまったく出なくなった

ということは十分あり得る。

ただし、

> ID 7が出なくなった = ドライブが完全に正常になった

とは限らない。

問題領域にアクセスしなくなっただけという可能性もある。

---

## 今回確認された状況

今回のPCでは、一時期、

- ソース：`Disk`
- イベントID：`7`
- 数日間継続
- 1日100件以上発生

という状態だった。

その後、Windowsに**新しいユーザーアカウントを作成し、そちらを普段使うよう変更した**。

約1か月後に確認したところ、新しいアカウントで作業するようになって以降、Disk / ID 7は一切発生していなかった。

これは重要な変化である。

なお、Windowsの「システム」イベントログはユーザーアカウント単位ではなくPC全体で共有される。

そのため、

> 新アカウントでイベントビューアーを開いたから旧アカウント時代のエラーが見えなくなった

ということではない。

新アカウントへ移行後、本当にID 7の発生自体が止まっていると考えられる。

---

## 旧ユーザープロファイルとID 7の関係

ここで考えられるのは、「旧ユーザープロファイルそのものがストレージを壊していた」ということではない。

より正確には、

> **旧プロファイルが頻繁にアクセスしていたファイルの保存領域と、ストレージ上の問題領域が重なっていた**

可能性がある。

関係を単純化すると、

```
旧ユーザープロファイル
        ↓
特定のファイルを読み書き
        ↓
そのファイルが保存されているSSD/HDD上の領域
        ↓
読み書きに失敗
        ↓
Disk / イベントID 7
```

という形になる。

ここで問題なのは原則として**ファイルの内容ではなく、ファイルが保存されているストレージ領域**である。

例えば、

- ブラウザキャッシュ
- AppData内のアプリ設定
- データベース
- Tempファイル
- Windowsのユーザー設定
- 検索関連データ

など、ログイン中に何度もアクセスされるファイルが問題領域に置かれていた場合、同じ場所を何度も読み込もうとしてID 7が大量発生することが考えられる。

正常なJPEGや設定ファイルであっても、その実データが読み取り不能な領域に存在すればストレージエラーになり得る。

逆に、ファイルの構造自体が壊れているだけでSSD/HDDが正常なら、通常はアプリケーション側の「ファイルを開けない」「データが破損している」などのエラーになり、Disk / ID 7とは別問題になる。

---

## 新アカウントでID 7が出なくなった理由として考えられること

主に次の可能性がある。

|可能性|内容|
|---|---|
|旧プロファイル内のファイルが問題領域を使っていた|新プロファイルではそのファイルへアクセスしなくなったため発生しなくなった|
|問題領域に現在アクセスしていない|問題そのものは残っているが、通常作業では踏んでいない|
|ドライブ側で代替処理された|問題ブロックが予備領域などへ置き換えられた|
|一時的なI/O障害だった|当時だけ発生した可能性もある|

特に、

> 旧アカウント使用中は大量発生  
> → 新アカウントへ変更  
> → 約1か月まったく発生なし

という時間的な対応があるため、旧プロファイルが利用していたデータ・領域との関係は疑う価値がある。

---

## 新しいアカウントでも将来再発する可能性

旧プロファイルのファイルが問題のある領域を使っていただけなら、現在ID 7が出ていなくても問題領域そのものが残っている可能性がある。

例えば、

```
旧ファイル
  ↓
問題領域を使用
  ↓
ID 7発生

新アカウントへ変更
  ↓
旧ファイルを読まなくなる
  ↓
ID 7停止
```

となっているだけかもしれない。

将来、その領域が空き領域となり、新しいファイルに再利用された場合、

```
問題領域
  ↓
新しいファイルが配置される
  ↓
読み書き
  ↓
再びID 7
```

となる可能性はある。

ただし、**確実に再発するわけではない。**

---

## SSDでは「同じ場所」の意味が単純ではない

HDDと違い、SSDではWindowsが認識する論理上の位置と、実際のNANDフラッシュ上の物理位置が必ずしも固定されていない。

概念的には、

```
Windows
  ↓
論理アドレス
  ↓
SSDコントローラー
  ↓
実際のNANDフラッシュ
```

という構造になっている。

SSD内部では、

- ウェアレベリング
- ガベージコレクション
- 不良ブロック管理
- 予備ブロックへの置換

などが行われる。

そのため、一度問題を起こした物理ブロックがSSD内部で使用停止になり、正常な予備ブロックへ置き換えられていれば、Windowsから同じ論理領域を再利用してもID 7は再発しない可能性がある。

したがって、

> 「以前問題のあった位置へ新しいファイルが置かれれば、必ずまたエラーになる」

とは言えない。

---

## 旧プロファイルを残して問題領域を塞ぐ案

旧プロファイルを削除せず残しておけば、そのファイルが使用しているファイルシステム上のクラスタは他の新しいファイルに再利用されにくい。

そのため、

> 旧プロファイルを残して問題領域を占有させておけば、新しいデータがそこへ作られず安全なのではないか

という考え方は一応成立する。

しかし、**恒久的な安全対策としては使えない。**

理由は以下。

- 旧プロファイルのファイルが問題領域を完全に固定しているとは限らない
- SSD内部の物理位置はWindowsから固定できない
- SSD側でデータ位置が変更される可能性がある
- Windows Defender、検索インデックス、バックアップなどが旧プロファイルへアクセスする可能性がある
- 問題領域が存在しているなら、それ自体をユーザーファイルで「塞ぐ」ことは正式な不良領域管理ではない

したがって、

> **旧プロファイルを残すことで偶然ID 7の再発を回避できる可能性はあるが、それを安全装置として頼るべきではない。**

旧プロファイルを当面残すのであれば、

> 問題領域を塞ぐため

ではなく、

> **原因調査のための証拠・比較対象として残しておく**

という意味合いの方が適切。

---

## 現時点での判断

今回の状況から確認できているのは、

- 過去にはDisk / ID 7が1日100件以上発生していた
- 数日間継続していた
- 新しいWindowsユーザーアカウントへ移行した
- その後約1か月、ID 7が一度も発生していない

という点。

このため、

> **現在進行形で同じストレージエラーが頻発している状態ではなさそう**

というのは良い材料。

一方で、

> **SSD/HDDが完全に正常であり、将来も問題が起こらない**

とまでは判断できない。

特に、新アカウントへの移行によって「問題領域を踏まなくなっただけ」の可能性は残る。

現状は、

> 過去に異常は存在したが、新環境では再現していない。  
> 原因領域が現在も残っているのか、SSD/HDD内部で処理されたのかはイベントログだけでは判別できない。

という整理になる。

---

## 次に確認するもの

旧プロファイルを削除したり、意図的に問題を再現させたりする前に、ストレージの状態そのものを確認した方がよい。

優先順位は、

1. 重要データのバックアップ確認
2. イベントビューアーで直近1か月の `Disk / ID 7` を確認
3. `51 / 129 / 153 / 157` など他のストレージ関連イベントも確認
4. CrystalDiskInfoなどでSMART情報を確認
5. 必要ならSSD/HDDメーカーの診断ツールを利用

となる。

HDDであれば特に、

- 代替処理済のセクタ数
- 代替処理保留中のセクタ数
- 回復不可能セクタ数

などが重要。

SSDの場合はメーカー・コントローラーによってSMART項目が異なるため、個別の値だけでなくSMART全体とメーカー診断を合わせて判断する。

今回のように過去に大量のID 7が記録されている場合、**「現在エラーが出ていない」という一点だけで異常なしと判断せず、SMART等で一度状態を確認しておくのが妥当**。
