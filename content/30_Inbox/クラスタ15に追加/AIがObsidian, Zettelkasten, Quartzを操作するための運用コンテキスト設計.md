# AIがObsidian / Zettelkasten / Quartzを操作するための運用コンテキスト設計

このノートは、AIがZettelkasten用のObsidian Vaultを操作するときに参照する専用コンテキストを設計した過程と、そこで確定した運用ルールをまとめたもの。

目的はクラスタリング手法そのものを説明することではない。クラスタリングやノート整理を行うAIが、

- どこへアクセスするか
- 各フォルダは何のために存在するか
- 何を読んでよいか
- 何を編集してよいか
- どの操作には人間の明示指示が必要か
- YAML、ファイル名、リンクをどう扱うか
- 統合・分割・削除をどう安全に処理するか

を理解するための、**Obsidian / Zettelkasten操作説明書**を作ることが目的となった。

最終的なコンテキストファイル名の第一候補は、

```
obsidian-zettelkasten-ai-operations-context.md
```

とした。

---

## 対象Vault

AIがZettelkasten関連作業で扱うルートは以下。

```
C:\Users\fukkamaru\Documents\GitHub\public\digital-garden\content
```

主な構成は次の通り。

```
content/
├─ .obsidian
├─ 01_Templates
├─ 02_images
├─ 10_Analytics
├─ 20_Journal
├─ 21_Reading
├─ 30_Inbox
├─ 31_Research
├─ 32_Zk
├─ index.md
├─ public-zettelkasten-build.md
└─ .gitkeep
```

このVaultでは、AIがフォルダ構成そのものを独断で変更することは原則禁止する。

## フォルダの役割とアクセス権限

|対象|役割|AIの扱い|
|---|---|---|
|`01_Templates`|Obsidian / Templater用テンプレート|参照のみ|
|`02_images`|画像格納|参照のみ|
|`10_Analytics`|Vault内データの確認・分析・Dataview・Bases・将来の統計表示|原則参照のみ|
|`20_Journal`|自分が行ったことの記録|参照のみ|
|`21_Reading`|読書ノート|参照のみ|
|`30_Inbox`|Fleeting等の未整理情報の受け皿|操作対象|
|`31_Research`|一次資料から生成した二次資料、Deep Research、AI整理資料等|操作対象|
|`32_Zk`|Zettelkasten本体|操作対象|
|`index.md`|Quartz公開サイトのHomeページ|参照のみ・操作禁止|
|`public-zettelkasten-build.md`|Zettelkasten構築について公開するノート|参照のみ・操作禁止|
|`.obsidian`|Obsidian設定|原則操作禁止|
|`.gitkeep`|Git管理用|原則操作禁止|

`10_Analytics`、`20_Journal`、`21_Reading`は通常参照専用だが、**既存Markdownリンクの機械的修正だけは例外的に許可**する。

一方で `index.md` と `public-zettelkasten-build.md` はリンク修正であってもAIが自動変更しない。影響がある場合は人間へ報告する。

## Inbox / Research / Zkの役割

この3フォルダは、単純な「未完成 → 完成」という一直線の状態遷移ではない。

### `30_Inbox`

ZettelkastenでいうFleeting相当を中心とした受け皿。

- 思いつき
- アイデア
- 見聞きしたこと
- 簡単なメモ
- 未整理情報
- 保存先未指定でAIが新規生成したノート

などを入れる。

AIが保存先の指定なしで新しいノートを作る場合は、原則として `30_Inbox` に保存する。

### `31_Research`

主として以下を置く。

- 一次資料からAIが生成した二次資料
- Deep Research結果
- AIによる整理・要約
- 一次資料の引用
- AI回答の保存
- 自分の言葉にまだ直していない資料

Researchは単なる「Zkになる前の未完成物」ではない。

Researchとして完結し、そのまま長期的に残ることも正常な状態とする。

`32_Zk`とはリンク可能。

### `32_Zk`

実際のZettelkasten本体。

- Permanent
- Literature
- Structure
- Index
- 一定程度読み物として成立したFleeting

などを置く。

---

## フォルダとノート種別は別の軸

このVaultでは、

> **フォルダ = ノート種別ではない**

という考え方を採用する。

たとえば `type: literature` は、

```
31_Research
32_Zk
```

のどちらにも存在し得る。

AIは、

> PermanentだからZkへ移そう

> LiteratureだからResearchへ移そう

などと、`type`だけを根拠にファイルを移動してはならない。

既存ノートの移動には人間の明示指示が必要。

---

## Zettelkastenのノート種別

YAMLの `type` には以下の5種類のみを使用する。

```
fleeting
literature
permanent
structure
index
```

`research`など、これ以外の値は作らない。

### Fleeting

思いつき、アイデア、見聞きした出来事などのメモ全般。

文章になっている必要はない。

基本的には、

> 思いついたこと、知ったことはすべてここから始まる

という位置付け。

### Literature

保存場所によって意味が異なる。

#### `31_Research` のLiterature

- 一次資料の引用そのもの
- AI生成回答のコピー
- 他者の文章
- 自分の言葉にまだ直していない情報

#### `32_Zk` のLiterature

他媒体やAI等から得た情報を、**自分自身の言葉に直したもの**。

### Permanent

1ノート・1トピックを基本とする。

そのノート単体で意味をなし、自分自身の考えとして清書されたカード。

Zettelkastenにおける最重要ノート。

### Structure

複数のPermanent Noteを体系的に整理し、思考の流れを意識して言葉でつなぐカード。

単なるリンク集ではない。

複雑な知識を整理しながら、新しい表現・アイデア・思考を継続的に生み出すための仕組みとして機能する。

### Index

全体または特定領域を俯瞰するための目次・索引。

基本的にはリンク集として機能する。

Structureのように、リンク同士を文章で思考的につなぐことは必須ではない。

## YAMLの基本構造

基準となるテンプレートは、

```
C:\Users\fukkamaru\Documents\GitHub\public\digital-garden\content\01_Templates\default.md
```

に存在する。

標準構造は以下。

```
---
title: 日本語タイトル
aliases:
  - 日本語タイトル
type:
created:
updated:
id:
permalink:
draft: true
tags:
---
```

ObsidianではTemplaterを利用している。

日時・IDの基準は、

```
created: YYYY-MM-DDTHH:mm:ssZ
updated: YYYY-MM-DDTHH:mm:ssZ
id: YYYYMMDD-HHmmss
```

AIが直接ノートを作る場合はTemplater式そのものではなく、その時点の実値を同じ書式で入力する。

既存ノートでは、

- `created`：変更しない
- `id`：変更しない
- `updated`：AIが内容を編集した場合に更新

とする。

YAMLのfield構造そのものを変更する場合は、人間からの明示指示が必要。

---

## title / aliases / filenameの役割分担

このVaultではそれぞれの役割が明確に分かれている。

```
英語ファイル名
→ Quartz上のURL

日本語title
→ Obsidian上で人間が読む表示名

aliases
→ 日本語でのリンク入力・検索支援
```

### title

原則日本語。

ノート内容を人間が識別しやすい、意味の明確な名称にする。

`type`ごとに別々の命名規則は設けない。

既存ノートの `title` を変更する場合は人間の明示指示が必要。

### aliases

絶対条件として、`aliases`には必ず `title` と完全同一の日本語名を最低1つ入れる。

```
title: AIとツェッテルカステン
aliases:
  - AIとツェッテルカステン
```

その後に別表記・別名を追加することは可能。

```
aliases:
  - AIとツェッテルカステン
  - ZettelkastenとAI
```

## permalink

Quartzでは別リンクとして扱われるが、本来期待していたpermalinkとしては機能しないことを確認済み。

field自体は残すが、

```
permalink:
```

基本的には空欄にする。

## draft

Quartzの公開制御に使う。

```
draft: true
→ Quartz上で非公開

draft: false
→ Quartz上で公開
```

新規ノートは必ず `draft: true` から始める。

AIが変更できるのは、人間から明示指示がある場合のみ。

---

## tags

現状の正式タグは以下。

```
field
ai-generated
reading
```

タグなしも可能。

複数タグも併用できる。

```
tags:
  - field
  - ai-generated
```

### field

ユーザー自身が**外部環境で実際に経験した内容**を記録したノートに付ける。

単なる外部情報・Web情報を意味するものではない。

`field`は人間が付与するタグであり、AIは自動付与しない。

人間から明示指示された場合のみAIが付与できる。

### reading

ユーザー自身の読書記録。

これも人間が付与するタグ。

AIは自動付与しない。

`reading` と `ai-generated` は併用しない。

### ai-generated

AIを使ったかどうかではなく、

> **最終的な思考・主張の主体がAIか人間か**

で判断する。

付与する例：

- AIがほぼ最初から最後まで生成した
- AIが資料を整理・要約して作った
- 人間自身の思考・価値判断・解釈がほとんど入っていない
- AIによる再構成によって、元の人間の考えとは違う方向の主張へ変化した

付与しない例：

- 軽微な誤字修正
- 表記統一
- AIによる単純な情報追加
- AIが大幅に文章整理していても、人間の元の考え・主張・方向性が維持されている

AI生成ノートを後から人間が大幅に書き直し、自分自身の思考へ昇華した場合は、人間の手で `ai-generated` を外す。

AIは自動削除しない。

`field`との併用は可能。

## 新規ファイル名のルール

Quartzでは実ファイル名がURLとなるため、新規ノートには原則として意味のある英語slugを使う。

形式：

```
lowercase-kebab-case.md
```

ルールは以下。

- 自然な英語
- 直訳より意味の正確さ・自然さを優先
- lowercase
- ハイフン区切り
- underscoreを使わない
- 空白を使わない
- 日本語を使わない
- 不要なstopwordは省く
- 通常3〜6単語程度
- 長くても8単語前後
- 短くすることで意味が曖昧になる場合は意味を優先
- IDや日時をファイル名に入れない

以前は専用GPTで1〜3候補を出して人間が選択していたが、AIによる新規ノート作成では、AIが最適な1案を自動決定する。

重大な意味分岐がある場合だけ人間へ確認する。

---

## ファイル名はVault全体でユニークにする

Obsidianでは**最短経路パス**を採用している。

そのため、Vault内のMarkdownファイル名には一意性が必要。

AIが新規ノートを作る場合やリネームする場合は、同名ファイルが存在しないことを確認する。

---

## Markdownリンク

WikilinkではなくMarkdownリンクを基本とする。

```
[日本語表示名](english-file-name.md)
```

表示名には原則としてリンク先ノートの `title` と同じ日本語名を使う。

### 最短経路パス

フォルダをまたぐ場合でも、

```
[タイトル](note-name.md)
```

を使う。

以下のような相対パスは原則使わない。

```
[タイトル](../32_Zk/note-name.md)
```

理由は、フォルダ移動や再編によって内容と関係のないGit差分が大量に発生するのを防ぐため。

---

## 未作成ノートへのリンク

リンク先がまだ存在しなくても、

```
[将来作るノート](future-note.md)
```

のようにリンク構造だけを先に置いてよい。

dead linkがあることだけを理由に、AIが自動的にリンク先ノートを作る必要はない。

ただし、

- ノートを作る合理的理由がある
- 人間から作成指示がある

場合は新規ノートを作れる。

---

## リンク追加・修正

既存ノートへの**新規リンク追加**は明示指示時のみ。

ただし、

> 新規ノートを作成して

という指示には、その新規ノート内部へ合理的な関連リンクを追加することまで含まれる。

既存リンクの機械的修正は通常可。

---

## AIの操作権限

|操作|権限|
|---|---|
|既存本文の校正|明示指示時のみ|
|本文構成変更|明示指示時のみ|
|情報追加|明示指示時のみ|
|YAML値の機械的整合性維持|通常可|
|YAML field構造変更|明示指示時のみ|
|既存title変更|明示指示時のみ|
|type変更|明示指示時のみ|
|draft変更|明示指示時のみ|
|field付与|明示指示時のみ|
|reading付与|明示指示時のみ|
|新規ノート作成|通常可|
|フォルダ構成変更|原則不可|
|ファイル移動|明示指示時のみ|
|新規リンク追加|明示指示時のみ|
|既存リンク修正|通常可|
|ファイル名変更|明示指示時のみ|
|ノート統合|明示指示＋破壊的処理直前確認|
|ノート分割|明示指示＋破壊的変更時の直前確認|
|削除|明示指示＋実行直前確認|

重要なのは、

> **一つの指示を別の操作権限まで勝手に拡張しない**

こと。

「校正して」と言われた場合に、構成変更・情報追加・ファイル移動まで勝手に行わない。

## 新規ノート作成

保存先指定なし：

```
30_Inbox
```

へ保存。

保存先指定あり：

指定フォルダへ直接作成可能。

作成時は、

1. 日本語 `title`
2. `aliases` にtitle同値
3. `type`
4. ユニークな英語slug
5. `created / updated / id`
6. 空欄の `permalink`
7. `draft: true`
8. 必要な `tags`

を設定する。

---

## ファイル移動

既存ファイルの移動は明示指示時のみ。

AIが内容や `type` を見て、

```
30_Inbox → 31_Research
31_Research → 32_Zk
```

などを勝手に行わない。

---

## リネーム

既存ファイルのリネームは明示指示時のみ。

実行時には、

- 新ファイル名の一意性
- inbound link
- 修正可能な既存リンク
- 操作禁止ファイルからの参照

を確認する。

以下では機械的なリンク修正可。

```
10_Analytics
20_Journal
21_Reading
30_Inbox
31_Research
32_Zk
```

以下は自動変更しない。

```
index.md
public-zettelkasten-build.md
01_Templates
02_images
.obsidian
.gitkeep
```

通常のリネームはChange Logには残さない。

---

## ノート統合

統合には人間の明示指示が必要。

統合元ノートを削除するなど破壊的処理の直前には、再度確認する。

原則として既存ノートの1つを存続先とする。

既存ノートのどれも統合後の内容を適切に代表しない場合は、新規ノートを作ってもよい。

統合指示には必要な本文再構成まで含まれる。

ただし、元ノートに存在しなかった新しい主張・情報をAIが勝手に追加してはいけない。

統合元への既存リンクは、意味的に適切なら統合先へ付け替える。

適切に置換できないものは自動変更せず報告する。

統合後には、

- 統合元ファイル一覧
- 統合先ノートへのリンク
- 統合理由
- リンク処理

などをChange Logへ残す。

---

## ノート分割

分割にも明示指示が必要。

元ノートを削除・大幅変更する場合は直前確認を行う。

分割後の元ノートの扱いはケースごとに判断する。

内容上自然な場合は、

> 元ノートをStructure Note的な索引として残し、分割先ノートへのリンクを置く

方法を推奨。

### 分割先の保存場所

分割元の思考主体によって決める。

```
人間自身の思考・主張が中心
→ 原則、分割元と同じフォルダ

AI生成主体
→ 原則、30_Inbox

判断できない
→ 人間へ確認
```

分割後には「分割元 → 分割先一覧」をChange Logへ記録する。

---

## ノート削除

削除は、

> **人間の明示指示＋実行直前確認**

が必須。

削除前には、

- filename
- title
- folder
- type
- inbound links
- 操作禁止ページからの参照

を確認する。

### 削除後のリンク

削除対象へのリンクは完全には消さない。

```
[削除対象](deleted-note.md)
```

を、

```
~~[削除対象](deleted-note.md)~~
```

へ変更する。

これによって、

- 過去にどのノートへリンクしていたか
- 現在は消失している

ことを同時に残す。

---

## 変更履歴

統合・分割・削除は後から追跡可能にする。

保存先：

```
10_Analytics/zettelkasten-change-log.md
```

途中では、

- `90_Operations`
- `10_Meta`
- `10_Observability`

なども検討した。

しかし `10_Analytics` は、

- Dataview等によるデータ確認
- Obsidian Bases
- Vault分析
- 将来的なQuartz統計ページ

という既存用途との連続性があり、Zkをフォルダ一覧の末尾に維持できるため、現状の名前を継続することにした。

`10_Observability`は次点候補。

---

## Change Logの仕様

通常ノートと同じメタ構造を使用し、`type`は `structure`。

AIが主に記述するファイルだが、**例外として `ai-generated` は付けない**。

記録対象：

```
統合
分割
削除
```

記録しない：

```
通常のリネーム
通常のファイル移動
```

新しい履歴を上へ追加する逆時系列形式。

各エントリでは、

- 日時
- 操作種別
- 対象
- 統合先・分割先など
- 理由
- リンク処理

を簡潔に残す。

削除済み・統合元など消失したノートは、

```
~~[旧タイトル](old-note.md)~~
```

として記録する。

削除理由が分からない場合、AIが勝手に理由を推測して書かない。

---

## 作業開始前：PRE-FLIGHT

AIは実際の編集前に以下を確認する。

1. 依頼内容
2. 対象ファイル・フォルダ
3. 対象領域の操作権限
4. 今回明示的に許可された操作
5. YAML
6. `type`
7. `draft`
8. `field / ai-generated / reading`
9. 必要な影響範囲
10. 新規作成・リネーム時のfilename一意性

新規ノート作成時には `01_Templates/default.md` も参照する。

Vault全体を理由なく一括走査しない。

ただし、

- backlink確認
- リンク修正
- 横断検索
- 指示されたクラスタ調査

など、作業達成に必要な範囲での横断検索は可能。

---

## 作業中：EXECUTION

AIは、

- 指示された範囲だけ変更する
- YAML規則を維持する
- 最短経路リンクを維持する
- 不要な情報を追加しない
- フォルダ構成を勝手に変えない
- 人間の思考をAIの思考へ勝手に変えない
- 操作禁止領域を変更しない

ことを守る。

破壊的操作では実行直前確認を行う。

---

## 作業終了前：POST-FLIGHT

終了前に以下を確認する。

- `updated`を更新したか
- `created`を変更していないか
- `id`を変更していないか
- `aliases`に`title`同値があるか
- `draft`を指示なく変更していないか
- `type`を指示なく変更していないか
- `field / reading`を自動付与していないか
- `ai-generated`判定は適切か
- filenameはユニークか
- リンク切れを不用意に作っていないか
- 操作禁止領域を変更していないか
- 統合・分割・削除ならChange Logを更新したか

## このコンテキストで重視する考え方

AIは、このVaultにおける知識管理の主体ではない。

AIは人間のZettelkastenを安全に操作する補助者として使う。

そのため、

- 人間の意味付けを勝手に変更しない
- ノート種別を勝手に昇格・降格しない
- ファイルを勝手に移動しない
- 人間の思考をAIの思考へ置き換えない
- 不明な点を推測で処理しない
- 破壊的操作を黙って行わない

ことを基本とする。
