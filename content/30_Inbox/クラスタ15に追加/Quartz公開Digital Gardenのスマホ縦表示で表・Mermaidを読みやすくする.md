# Quartz公開Digital Gardenのスマホ縦表示で表・Mermaidを読みやすくする

Quartzで公開しているDigital Gardenをスマートフォンで閲覧すると、横向きでは比較的読みやすい一方、縦向きでは本文幅が狭くなるため、**Markdown表やMermaid図の可読性が大きく低下する**。

この問題は、単純にフォントを小さくしたり、すべてを画面幅へ縮小したりするのではなく、**表とMermaidをそれぞれの性質に合った方法で表示する**のがよい。

基本方針は次の通り。

|コンテンツ|スマホ縦表示での基本方針|
|---|---|
|通常本文|従来どおりレスポンシブ表示|
|Markdown表|列幅を潰さず、必要なら横スクロール|
|Mermaid|本文では全体像を表示し、詳細は全画面・ズーム|
|巨大な表|最低幅を持たせて横スクロール|
|巨大なMermaid|全画面表示、または図そのものを分割|
|本文余白|補助的に少し縮める|

重要なのは、**PC用とスマホ用でMarkdownを二重管理しないこと**。表示上の問題なので、可能な限りQuartz側で吸収する。

---

## 発生している問題

スマートフォンを縦向きにすると、本文領域が狭いため、横長の情報構造が無理に圧縮される。

特に表では、第一列の項目名が、

```
日本
語訳・
基本義
```

のように数文字ごとに折り返されることがある。

今回確認したような、

|残すもの|役割|
|---|---|
|日本語訳・基本義|最低限の確認|
|使用感・ニュアンス|似た語との違い、使う場面など|
|語源・語族|なぜ意味がつながるかを考える入口|
|実例・関連概念|既知の内容へ接続する材料|
|自分の疑問|後で調べ直す理由を残す|

といった「項目＋説明」型の表では、左列が極端に細くなると特に読みづらい。

問題の本質は、

> 横長の情報を、スマホ縦画面の狭い本文幅へ無理に収めようとしていること

にある。

---

## 表は「縮小」より横スクロールを優先する

表については、すべての列を画面内へ押し込むより、**最低限必要な列幅を維持したまま左右へスクロールできるようにする**方が読みやすい。

イメージは次のようになる。

```
┌─────────────────────────────────────────┐
│ 日本語訳・基本義 │ 最低限の確認。大量に蓄積するなら… │
│ 使用感・ニュアンス│ 似た語との違い、使う場面…          │
└─────────────────────────────────────────┘
                ← 左右スクロール →
```

スマホ画面から表の右側がはみ出すこと自体は問題ではない。

むしろ、

> 表全体を見せるために、一つ一つのセルを読めなくする

方が問題になる。

### 第一列の最低幅を確保する

今回のような日本語表では、第一列に、

- 日本語訳・基本義
- 使用感・ニュアンス
- 語源・語族
- 実例・関連概念
- 自分の疑問

のようなラベルが入る。

これらは細かく折り返すより、一定の横幅を確保した方がよい。

実装時には、概念的には次のようなCSSが候補になる。

```
@media (max-width: 600px) {
  .table-container {
    overflow-x: auto;
    -webkit-overflow-scrolling: touch;
  }

  .table-container > table {
    min-width: 36rem;
  }

  .table-container th:first-child,
  .table-container td:first-child {
    min-width: 8em;
    word-break: keep-all;
  }
}
```

ここで重要なのは数値そのものではなく、

- 表に最低幅を持たせる
- 第一列を必要以上に狭めない
- 親要素を横スクロール可能にする

という考え方。

実際のQuartz環境に合わせてセレクタや幅は調整する必要がある。

---

## すべての表を一律に巨大化しない

一方で、すべての表へ大きな `min-width` を設定するのも適切ではない。

例えば、

```
項目 | 値
A    | 10
B    | 20
```

程度の小さな表まで強制的に横スクロールになると、逆に使いづらい。

そのため基本は、

1. 通常の表はそのまま表示
2. スマホで列が潰れる表だけ最低幅を確保
3. 特殊な巨大表だけ追加対応

という順序がよい。

長期運用を考えるなら、ページごとの例外指定を大量に増やすより、**一般的な表は自動的にそれなりに読める状態にしておく**方が管理しやすい。

---

## 「項目＋説明」の2列表はカード表示とも相性がよい

今回の表は、厳密には比較表というより、

```
項目
↓
その項目の説明
```

の集合になっている。

そのため、スマホでは次のようなカード型や定義リスト型の表示も考えられる。

```
日本語訳・基本義
最低限の確認。大量に蓄積するなら……

────────────

使用感・ニュアンス
似た語との違い、使う場面……

────────────

語源・語族
なぜ意味がつながるか……
```

今回の表だけを考えるなら、この形式はかなり読みやすい。

しかし、これを**すべてのMarkdown表へ自動適用するのは避けた方がよい**。

例えば、

- 製品比較
- 価格比較
- PCスペック比較
- 年代別データ
- 数値表
- 複数候補の比較表

では、横方向の対応関係そのものが重要になる。

カード化すると、

> どの値がどの列と対応しているのか

が分かりにくくなる。

したがってカード化は、

> 「項目｜説明」の単純な2列表だけに限定する

なら候補になる。

ただし、自動判定や専用クラスなどが必要になり、単純な横スクロールより実装・保守コストは上がる。

---

## Mermaidは表と同じ方法では解決しにくい

Mermaidも横長になりやすいが、表と同じように単純な横スクロールへするだけでは使いにくい。

表は一部分だけを順番に読んでも成立しやすい。

しかしMermaidでは、

- ノード同士の関係
- 上下関係
- 左右関係
- 分岐
- 接続線
- 全体構造

を見ながら理解する必要がある。

そのため、

```
Mermaid
↓
横スクロール
```

だけでは、図の一部分しか見えず、全体像を把握しづらくなる。

---

## Mermaidは「通常表示＋全画面ビューア」が向いている

Mermaidについては、本文内ではまず図全体を表示し、必要なときだけ拡大できる構造がよい。

通常の記事では、

```
文章

┌──────────────────┐
│                  │
│     Mermaid      │
│      diagram     │
│                  │
└──────────────────┘

文章
```

として全体像を確認できる。

細部を確認したいときだけタップして、

```
┌──────────────────────────┐
│ ×                        │
│                          │
│          Mermaid         │
│                          │
│  ピンチ：拡大・縮小      │
│  ドラッグ：移動          │
│                          │
└──────────────────────────┘
```

のような全画面ビューアへ移る。

この方式なら、

- PC
- タブレット
- スマホ横向き
- スマホ縦向き

のすべてで同じMermaidソースを使える。

## 巨大なMermaidは分割する

非常に大きな図は、ビューア機能だけで解決しようとせず、図自体を分割する方法もある。

例えば、

```
全体図
├─ 詳細図A
├─ 詳細図B
└─ 詳細図C
```

という構成にする。

これは単なるスマホ対策ではなく、ZettelkastenやDigital Gardenとしても、

> 一つの図へ情報を詰め込みすぎない

という情報設計上の利点がある。

---

## 本文左右の余白を縮める方法は補助策

スマホでは、本文左右の余白を少し狭くすることでも表示幅を増やせる。

例えば、

```
画面幅       390px
左右余白      32px
本文幅       358px
```

だったものを、

```
画面幅       390px
左右余白      20px
本文幅       370px
```

程度へ変更すれば、多少使える幅が増える。

ただし、増えるのは十数px程度なので、

> 余白を減らせば横長表やMermaidの問題が解決する

わけではない。

あくまで、

1. 表・Mermaid自体の表示方法を改善
2. そのうえで余白を微調整

という順序にする。

## 実装するなら優先順位

今回確認した実際の縦表示を基準にすると、優先順位は次の順がよい。

1. **Markdown表の列潰れを防止する**
    - 第一列の最低幅
    - 不自然な単語途中改行の防止
    - 横スクロール
2. **Mermaidの全画面ビューアを追加する**
    - タップで開く
    - ピンチズーム
    - ドラッグ移動
    - 閉じる
3. **スマホ本文の左右余白を微調整する**
4. 必要になった段階で、
    - 「項目＋説明」型2列表のカード表示
    - 特に巨大な表の個別対応
    - Mermaidのレイアウト変更
    - Mermaidの分割

を検討する。

## 実装前に確認すること

具体的なCSSやJavaScriptを実装する前に、現在使用しているQuartz環境を確認する。

特に、

- Quartzのバージョン

- 既存のスマホ向けCSS
- SPA遷移時の再初期化が必要か
- 既存カスタマイズと競合しないか

を確認してから実装する。

これらを確認せずにセレクタを固定すると、Quartzの構成によってはCSSやJavaScriptが効かない可能性がある。

## 結論

Quartzで公開するDigital Gardenのスマホ縦表示では、**すべてを狭い画面内へ押し込むことを目標にしない**。

コンテンツの性質ごとに、

- **表は横幅を維持して横スクロール**
- **Mermaidは本文で全体像、詳細は全画面＋パン・ズーム**
- **余白調整は補助的に使用**

とする方が読みやすい。

また、この問題をObsidian側のノートへ持ち込まず、

> **Obsidian Markdownは意味構造を保ち、表示上のレスポンシブ対応はQuartz側で処理する**

という分離を維持する。

これにより、今後ノートや表、Mermaidが増えても、PC用・スマホ用のコンテンツを二重管理せずに済み、Digital Garden全体の保守性を維持できる。
