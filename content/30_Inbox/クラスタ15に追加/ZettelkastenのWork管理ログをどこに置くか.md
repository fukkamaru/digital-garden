# ZettelkastenのWork管理ログをどこに置くか

Zettelkastenの整理・再編をChatGPT Workで継続して行う場合、作業ログをどの単位で分割し、どこに保存するかを整理した。

結論として、**作業ログを1作業ごとに細分化する必要はない**。また、現在 `30_Inbox` を一時的な作業場として使っているが、Zettelkastenの保守・再編作業を継続するのであれば、**専用の作業管理フォルダを新設し、Inboxから作業管理機能を分離する方がよい**。

---

## ログは「1作業1ファイル」では細かすぎる

Zettelkasten再編では、

- 親クラスタ
- 子クラスタ
- 個別ノート

という階層で処理することが多い。

このとき、個別作業ごとにログファイルを作ると、

- ログファイルそのものが大量に増える
- 一連の判断経緯が複数ファイルへ分散する
- Workが過去ログを探す負担が増える
- 人間側からも履歴を追いにくくなる
- ファイル作成・命名・リンク管理が新たな作業になる

という問題が生じる。

一方で、Zettelkasten全体を1つの巨大ログへ書き続けると、今度はログが肥大化し、Workが再開時に読むコンテキスト量が増える。

そのため、

> **記録頻度は子クラスタ単位、ファイル分割は親クラスタ単位**

くらいが適切。

```
Parent cluster A
└─ log-a.md
   ├─ Subcluster A-1
   ├─ Subcluster A-2
   └─ Subcluster A-3

Parent cluster B
└─ log-b.md
```

個々の処理内容を完全な操作履歴として残すのではなく、以下を中心に記録する。

- 何を処理したか
- 統合・分割・移動などの重要な変更
- 判断理由
- 未解決事項
- 次に行うべき処理
- 作業中に発見した問題

---

## Workログとコンテキストは別物

ここでいう「コンテキスト保存側」とは、`04_Context` の中にログを置くという意味ではなく、AI向けのコンテキストや運用資料を保管している領域全体を指す。

ただし、Workログそのものは長期的なAIコンテキストとは性質が異なる。

```
Context
= 次の作業を正しく始めるための前提・ルール

Work Log
= 過去の作業を追跡・復元するための履歴
```

たとえば、

- Markdownリンクの扱い
- Permanent判定基準
- AIの編集権限
- ファイル命名規則

などは、今後も繰り返し利用するためコンテキストや運用ルールとして保存する。

一方、

- Cluster Aで12ノート確認した
- 3ノートを統合した
- 1件保留した
- 次回はSubcluster A-4から再開する

といった情報はWorkログに属する。

作業中に新しい共通ルールが確定した場合は、

```
flowchart LR
    A[作業] --> B[Work Log]
    B --> C{今後も使う判断か}
    C -->|No| B
    C -->|Yes| D[長期ルール・Context]
```

という形で、ログから長期コンテキストへ昇格させる。

## Zettelkasten内部に作業管理用の領域を設ける

今回の問題は、ログだけではなく、現在 `30_Inbox` が一時的な作業領域として使われていることにもある。

Inboxには本来、

- 新しく作ったメモ
- まだ分類していない情報
- あとで処理するノート

などを置く。

しかし現在は、それに加えて、

- クラスタ整理用ファイル
- 作業対象一覧
- Workの進捗管理
- 中間生成物
- 統合候補
- 監査用の一時資料

なども置かれている。

つまり、

```
未整理だからInboxにある

と

現在Workで作業しているからInboxにある
```

という2つの意味が混在している。

これは長期的には分離した方がよい。

---

## `03_...` を新設する案

Zettelkasten用フォルダの内部に、作業管理専用の `03` 系フォルダを新設する。

名称候補としては、

- `03_Work`
- `03_Maintenance`
- `03_Management`

などが考えられる。

`03_Zettelkasten-Work` のような名称は、すでにZettelkastenフォルダの内部に存在するため冗長。

用途が「AIによる再編作業・監査・統廃合・リンク修正など」であれば、`03_Work` または `03_Maintenance` が分かりやすい。

例：

```
Zettelkasten/
├─ 01_...
├─ 02_...
├─ 03_Work/
│  ├─ Status.md
│  ├─ Logs/
│  │  ├─ cluster-a.md
│  │  ├─ cluster-b.md
│  │  └─ cluster-c.md
│  └─ ...
│
├─ 30_Inbox/
├─ 31_Research/
└─ 32_Zk/
```

`03_Work` はZettelkastenの知識そのものではなく、

> **Zettelkastenを整理・維持・再編するための作業状態**

を置く領域になる。

## Inboxから移すもの

`30_Inbox` の全ファイルをそのまま `03_Work` へ移すわけではない。

基準は、

> **そのファイルは「Zettelkasten再編作業のためだけに存在しているか」**

で判断する。

|現在Inboxにあるもの|今後|
|---|---|
|新規メモ|`30_Inbox`|
|未分類ノート|`30_Inbox`|
|あとで知識化する情報|`30_Inbox`|
|親クラスタ・子クラスタの作業管理|`03_Work`|
|Work進捗ファイル|`03_Work`|
|Workログ|`03_Work`|
|クラスタ一覧|`03_Work`|
|統廃合候補一覧|`03_Work`|
|監査用の一時資料|`03_Work`|
|AI処理用の中間ファイル|`03_Work`|
|整理後のResearch資料|`31_Research`|
|Permanent / Literature / Structure等|`32_Zk`|

これにより `30_Inbox` を、本来のInbox用途へ戻せる。

```
flowchart TD
    I[30_Inbox 現在]
    I --> A[本来のInbox]
    I --> B[Work用の作業物]

    A --> NI[30_Inboxに残す]
    B --> W[03_Workへ移す]

    W --> R[31_Research]
    W --> Z[32_Zk]
```

## `03_Work` の役割

`03_Work` は恒久的な知識を保存する場所ではない。

主に、

- 現在の作業状態
- 作業ログ
- 処理対象一覧
- クラスタ管理
- 監査・統廃合候補
- 一時的な中間成果物
- 再開地点
- 未解決事項

を保持する。

一方で、

```
04_Context
→ AIが守るべき長期的な前提・運用ルール

30_Inbox
→ 未整理の新規情報

31_Research
→ 調査・資料

32_Zk
→ Zettelkasten本体

03_Work
→ Zettelkastenを整理・維持するための作業状態
```

という責務分離になる。

## 今回の判断

今回の議論では、次の方針が妥当。

1. Workログは「1作業1ファイル」にはしない。
2. 親クラスタ単位でログを分ける。
3. 子クラスタ完了時などに同じログへ追記する。
4. 長期ルールと作業履歴を分離する。
5. Zettelkasten内に `03_Work` などの作業管理領域を新設することを検討する。
6. 現在Inboxで行っている「作業管理」の部分を03側へ移す。
7. Inboxは本来の「未整理情報の入口」へ戻す。
8. Inboxからの移動は一括ではなく、作業専用ファイルかどうかを確認して行う。

この構造にすると、Workによる再編作業が増えても、Zettelkasten本体・Inbox・AIコンテキスト・作業履歴が混ざりにくくなる。

必要なら次に、**このノートを前提に `03_Work` の具体的な内部構成だけを詰めた設計案**も作れます。
